# Story Outline Authoring

First classify the request as either a **local setting patch** or a full authoring task.

- A local setting patch changes confirmed lore, a summary, tags, foreshadowing, or a small number of existing-node prose fields; it neither changes maturity/template status nor defines gameplay, maps, events, resources, entry/completion conditions, or a mainline direction. Read `AGENTS.md`, the target source node and Markdown, and only directly linked nodes needed to verify the stated relation. For a new or moved `side`, also use `$liluo-story-outline-graph-maintenance` to inspect the direct parent and its children. Apply the provenance gate, make the smallest synchronized JSON/Markdown edit, run one direct structural check when structured fields changed, and refresh/validate the project index once. Do not load the full outline template, world options, maturity references, mainline memo, plot catalog, or broad world sources unless the local patch expands into a design decision or reveals a conflict.
- For every other task, read the outline template, target world option, source node, Markdown, and only the parent, direct children or referenced material needed to resolve the requested scope. Once the source confirms the target container, do not repeat relationship retrieval in the same task unless the source changes, the scope is ambiguous, or a graph edit is proposed. Read [maturity-decision.md](references/maturity-decision.md) and [authoring-checklist.md](references/authoring-checklist.md). When the source node has `status: 主线任务`, or an ordinary node belongs to a mainline container, also read [mainline-reference.md](references/mainline-reference.md) and the relevant mainline memo Markdown.

For complex localization, query the current project index first; verify source JSON/Markdown before writing, then run `npm run project:index:changed` and `npm run project:index:validate` after indexed-source changes.

1. For a local setting patch, use the fast path above and do not promote it into a full design pass merely because it writes both JSON and Markdown. For all other tasks, check `status` before choosing a template. A `主线任务` node is a mainline container and reference backup, not an ordinary module: preserve confirmed direction with the mainline-reference structure, do not assign an ordinary maturity, and do not add module production fields. Only ordinary story nodes choose the highest honestly supported maturity.
   - Default to expanding the closest existing node or mainline memo. Create a child node only when the user explicitly requests a split, or the content demonstrably needs an independent playable scope, entry/completion conditions and production lifecycle; record the reason before creating it. Do not split merely because a new location, character, commission or idea appears, and never duplicate the same confirmed direction in both a memo and a child.
2. Before authoring an ordinary node under a mainline, follow `parentKey` upward and read the nearest relevant mainline memo, plus any upstream memo whose confirmed direction still governs the node. Treat “已确认方向” and confirmed continuity as constraints unless the user explicitly revises them; use recommended stages as design references rather than established facts; carry unresolved memo items into questions or ordinary-node `missingItems` only when they actually affect this node. Record the memo as context, but never copy its whole body into every child.
3. Ask only for decisions affecting world, primary tag, player flow, gameplay, states, branches or resources.
4. Never use fake IDs, `无`, filler, or copy a world candidate library.
5. When the user says an inspiration is not figured out, "待定" or "待做", preserve only the confirmed direction and register the unresolved decision as a concrete `missingItems` entry. Do not complete it, promote it into established plot, add an appearance/reference, or invent implementation details. Treat "待定" as workflow state, not filler prose.
6. Synchronize JSON and one Markdown file; verify key, title, filename, world, parentKey and missingItems. Before removing the final `missingItems` entry, reconstruct and audit the entire accumulated context, including source content, all prior accepted answers, the current answer, current maturity and confirmed scope. Check old answers again for incompleteness or conflict with newer decisions; resolved question lists do not prove completeness. If executable flow, gameplay rules, state changes, transitions, or first-version boundaries remain undecided, replace the old entries with concrete next-layer gaps.
7. Do not restructure relatives unless requested; route graph work to `$liluo-story-outline-graph-maintenance`.
8. Select the smallest story verification and do not stack overlapping checks. For prose-only Markdown edits that leave frontmatter, source JSON, keys, parent links and runtime references unchanged, use the directly relevant writing/originality check and skip story frontmatter plus the unified content validator. For frontmatter or source-JSON changes, run the smallest applicable story test or changed-scope validator; use both only when they cover materially different risks. Preserve data and report exact failures.
9. Before asking any question that may lead to outline write-back, or before making a user-authorized outline change that still requires a story decision, search `src/game/data/plot_outline/catalog.json` for unused entries and unresolved portions of partially used entries that plausibly match the confirmed world, characters, locations, conflict or player flow. Include real matches as concise optional choices in the same question, naming the plot entry and why it may fit. Do not add irrelevant candidates merely to fill options. Never insert one automatically or describe an unresolved portion as established plot.
10. After explicit adoption, synchronize the story, append its real key to `usedBy`, and set `usageStatus` to `partial` or `used`. Keep causally linked setup and payoff in one entry. Before assigning a new plot ID to an unresolved fragment, compare it with existing entries: merge it into an existing entry when it extends the same core conflict, causal chain, setup/payoff, or intentionally shared collection of segments, preserving the stable ID and usage state. A shared world, tag, character, or broad theme alone is not enough to merge. If merge versus split is ambiguous or conflicts with confirmed structure, ask the user. Only genuinely independent fragments receive the next stable ID, `isUsed: false`, `usageStatus: unused` and empty `usedBy`.
11. Format plot titles as `主要人物-短情节名`. Omit the default protagonist 璃落; list at most three other main characters and append `等` when more exist. Preserve stable keys in `usedBy`; format each matching `usedByLabels` value as `世界名-主线名-节点名` in Chinese.
12. Record every appearing character, including 璃落, in `characters`. Keep `storyTags` as the independent world/style taxonomy. Put non-bondage subject, setting, identity and structure labels in free-form `plotTags`; put only confirmed bondage methods or bondage themes in `bondageTags`. Never restore the retired ordinary `tags` field, inherit a bondage tag merely because an applied plot has it, or invent a bondage tag.
13. For large cross-node work, the parent may delegate read-only context reconstruction to `liluo_context_explorer` and continuity checks to `liluo_continuity_reviewer`. Subagents never edit story files; the parent synchronizes JSON and Markdown.
14. When the input is an approved story-gap candidate, read the candidate card, target source and authoritative context; verify its status is `accepted`, `accepted-with-changes`, or `expanded`. Do not repeat full gap discovery. Expand it through the normal template and approval rules; after an authorized write record the real story key, refresh the project index, and run applicable continuity/content/originality checks.

Before any formal write, apply `docs/系统说明/正式项目内容来源与版权写入门槛.md`; external RAG prose and reference-only material never become canon.
