# ADR-012：上下文分层与创作组有效参与机制

## 当前结论

项目配置可以继续增多，但默认装载必须分层：`project-navigation/context-policy.json` 作为唯一机器可读装载策略（L0–L4）。创作组默认 `immersive` 人格、`compact` 可见密度与 `actual-call-only` 参与规则三者分离；是否委派由 `project-navigation/team-routing.json` 的 `solo` / `micro-consult` / `council` 三档决定。Cursor 与 Codex 继续长期并存，只保留薄适配并共同引用普通权威文件。

## 背景与理由

配置数量本身不是故障；同等优先级装载会浪费上下文并稀释权威。同时，默认 `immersive` 与成员条目/`token-budget` 中的 `subtle` 冲突，容易把“沉浸”误解为高频多人对话，或把未调用成员写成正式参与者。需要机器可读策略与审计，而不是继续只靠自然语言提醒。

## 主要替代方案与代价

- 大规模删除 Skills/灵魂卡/文档以“变少”：会削弱能力，明确拒绝。
- 每次任务读取全员灵魂卡并召开多人讨论：成本高且不真实，明确拒绝。
- 在 `.cursor/` / `.codex/` 复制共同规则：双端漂移，违反 ADR-010，明确拒绝。
- 另建顶层 `context-system/` 目录：增加导航成本，明确拒绝；复用 `project-navigation/`。

## 影响范围

- 新增 `context-policy.json`、`team-routing.json`、对应 Schema、解析/审计命令与测试
- roster 升级到 schemaVersion 3，以 `presencePolicy` 取代冲突字段
- 更新创作组 Skill、系统说明、Cursor Always 规则与治理注册表
- 不引入第三方写作模型/API/MCP 正文服务
