# 项目概览

`璃落宇宙` 是一个 AI 原生叙事游戏生产体系，目标不是只完成一条单一产线，而是让同一宇宙中的故事、角色、关系、状态和氛围，能够被持续生产成多种正式体验形态。

`璃落的城堡` 仍然是当前最重要的旗舰实例。它首先要成为一个真正可游玩、可扩展、可长期积累的像素风冒险 RPG，同时也要具备把同一叙事拆成互动小说、副本桥段、CG 简报和资料性表达的能力。

## 核心方向

- 用统一正史支撑多种体验形态，而不是为每种形态各写一套事实。
- 用叙事生产包把故事节点转成可复用、可验证、可扩展的制作合同。
- 让像素风 RPG 继续承担旗舰世界体验，让互动小说与轻量形态承担低成本验证和局部放大。
- 让 AI 正式参与检索、提案、编排、验证和维护，而不是只做临时写手。
- 让素材、玩法、文档、Schema、工作流和索引都服务于长期内容生产。

## 技术栈

当前项目主要使用：

- Vue 3
- Vite
- Phaser，用于 2D 地图、移动、碰撞和事件
- Pinia
- Vue Router

旧 README 中还记录过 Arco Design Vue、Vant、Lodash、Clipboard、File Saver、Pinyin、Segmentit 等依赖。当前是否继续使用，以 `package.json` 和实际代码为准。

## 运行命令

```powershell
npm install
npm run dev
npm run build:web
npm run build:offline
npm run package:offline
npm run preview
```

常用说明：

- `npm run dev`：启动 Vite 开发服务。
- `npm run build:web`：普通 Web 构建。
- `npm run build:offline`：生成可双击入口的多文件离线构建。
- `npm run package:offline`：校验离线产物并生成 ZIP。
- `npm run preview`：预览构建结果。
- `npm run map:trim-empty-border`：地图空白边界修剪脚本。

项目知识索引、外部知识库、内容维护及 Git 发布命令统一见 [用户命令目录](./用户命令目录.md)。

## 五层生产架构

```text
宇宙与正史层
  -> 叙事生产层
    -> 体验编排层
      -> 素材编排层
        -> 输出与运行层
```

- 宇宙与正史层：维护世界、角色、关系、故事节点和正式状态。
- 叙事生产层：把批准过的故事拆成叙事生产包，明确目标、约束、输出形态和素材槽位。
- 体验编排层：把同一叙事安排进 RPG、互动小说、副本、桥段稿和资料表达。
- 素材编排层：为同一叙事准备可渐进增强的立绘、CG、音频、地图资源和 UI 资产。
- 输出与运行层：把产物接入当前 Phaser 运行时和未来可扩展的其他承载形态。

## `src/game` 职责

- `core/`：跨场景基础能力，包括游戏创建、场景 key、事件/对话运行、玩家运行时状态。
- `scenes/`：Phaser 场景本体，目前按 `BootScene -> MapLoadingScene -> WorldScene` 串主流程。
- `systems/`：可复用运行逻辑，不直接承担场景生命周期。
- `systems/map/`：地图加载、出生点、碰撞、寻路、镜头、运行时整理、地图渲染等地图核心逻辑。
- `systems/character/`：玩家移动、输入、路径预览等角色控制逻辑。
- `systems/animation/`：角色与世界动画注册、资源准备和复用逻辑。
- `systems/environment/`：昼夜、天气、雾层等地图环境表现。
- `data/`：游戏数据、资源清单、配置与注册表。
- `data/maps/<mapId>/`：单张地图自己的数据目录，常用 `map.json`、`events.json`、`dialogues.json`、`meta.ts`、`assets.ts`。
- `data/interactive_fictions/<scenarioId>/`：单个互动小说/副本数据目录，是正式输出形态之一。
- `views/`：Vue 侧游戏挂载容器、模式 UI 与桥接逻辑。

## 开发原则

- 先保证可玩，再补细节。
- 先保证旗舰主流程，再扩充多形态输出。
- 地图、事件、对话、存档仍是旗舰体验核心。
- 互动小说、桥段稿、资料页和 CG 简报是正式生产形态，不是失败回退。
- 新内容优先服务地图移动、发现地点、触发事件、推进剧情、形成记忆点，以及同一叙事的后续复用能力。

## 文档原则

功能真正完成，并且经过用户实际测试确认无报错后，需要补充功能更新文档。

文档至少记录：

- 实现思路
- 相关代码路径
- 开发过程中遇到的问题
- 对应问题的解决方法
- 验证结果

历史记录保留在 `docs/功能更新/`，当前系统说明沉淀到 `docs/系统说明/`。

根 `README.md` 负责项目总入口与定位摘要；`docs/README.md` 负责文档导航；`docs/用户命令目录.md` 负责长期用户指令与脚本速查。三者不重复保存大段系统细节。
