# 故事大纲随机提问模板

本模板用于“随机选择一个故事条目，给出上下文，再根据待补内容向用户提问”。可用于任意世界，不限于都市。

## 一、选择范围

1. 用户指定世界时，只在该世界内随机选择。
2. 用户未指定世界时，在全部世界中随机选择。
3. 默认只选择含有 `missingItems` 的普通故事节点，不选“分类”“主线任务”“收回”节点。
4. 随机结果必须来自实际候选池，不得因为某个条目更熟悉而主动指定。

## 二、提问前必须读取的上下文

### 轻量随机路径

用户说“随机”“随便”“问一个”，或没有提出筛选、比较和检索条件时：

- 直接从真实候选池随机选择，不调用子智能体。
- 只读取来源 JSON 中的抽中节点及其对应 Markdown。
- 不默认展开父节点、子节点、同级节点、世界选项、玩法目录或情节目录。
- 只有某条直接引用对于避免重复提问不可缺少时，才补读该引用。

### 检索筛选路径

只有用户明确要求“找最完整的”“找最接近某条件的”“比较后选择”“检索匹配项”等需要跨节点证据的结果时，才进行扩展检索，并可按需委派只读智能体。此时根据筛选目标读取必要的父子节点、同级节点、世界资料、玩法引用或情节目录，不做无边界扫描。

两条路径都必须读取项目中已经能直接回答该节点缺口的真实资料，不得把可确认的问题重新丢给用户。

## 三、上下文输出格式

先输出“随机抽到的条目”，再用简短列表说明：

- 所属世界与主要风格。
- 当前成熟度。
- 父节点、子节点和条目在故事链中的位置。
- 现有核心概念。
- 已确认的角色、地点、玩法、状态或规则。
- 本轮优先追问的缺口，以及明确跳过的地图、音频等项。

上下文只写项目已确认内容，不把提问时的候选方向写成既定设定。

轻量随机路径未读取父子链时，省略父子关系，不得为凑齐格式而额外检索或推断。

## 四、待补项的询问优先级

优先询问可以通过文字直接回答、且会改变条目设计的元数据：

1. 与父节点、子节点及世界主线的关系。
2. 玩家或璃落的进入条件、初始状态和同行角色。
3. 主要目标、核心冲突和可执行的操作循环。
4. 关键角色的身份、动机、关系、立场和隐瞒信息。
5. 身体、能力、道具、拘束或其他会改变操作的状态。
6. 阶段目标、完成条件、失败后果、恢复方式和离开方式。
7. 分支选择、结局差异、状态写入和对后续条目的影响。
8. 是一次性事件、短篇、长篇，还是可重复、可扩展的长期区域。

默认暂不询问：

- 地图瓦片、精确尺寸、完整路线和场景制作细节。
- 背景音乐、音效、声优、混音和音频文件。
- 立绘、像素动画、精灵表和特效制作规格。
- 用户当下无法直接回答的工程实现问题。

如果 CG、场景图或动画的“叙事内容”本身会改变剧情，可以询问“画面发生在哪个时机、出现谁、定格什么事件”，但不问分辨率、文件格式或制作工时。

## 五、具体提问规则

每个问题应尽量包含以下三层：

1. **具体对象**：点名条目、区域、角色、前置事件或现有机制。
2. **需要决定的事**：只聚焦一个会影响设计的核心选择。
3. **灵感支架**：说明这个答案会影响什么，并给出 3–6 个符合现有资料的参考方向。

参考方向应尽量丰富并保持实质差异，不只换词重复同一方案。选项默认不是单选题，用户可以多选、组合、修改、全部否定或提出新方案；选项只是灵感支架，不能自动成为既定设定，最终以用户明确指定为准。用户选择的多个方向彼此冲突，或与累计确认上下文冲突时，必须指出具体冲突并请用户决定取舍，不得擅自拼接、覆盖旧答案或替用户解释。

反例：

> 请补充地图。

改写为：

> 璃落第一次从《永拘迷宫》误入《阈限空间》时，具体是触发了哪种事件？例如打开不该存在的门、被实体追入维护通道、触碰异能节点，或在某次循环后从现实“卡出”？这会决定首次进入是偶然、追逐结果还是主动调查。

反例：

> 请补充玩法。

改写为：

> 在已确定的“无尽走廊、空间循环和实体追赶”中，玩家每 5–10 分钟反复执行的主要循环是什么？可以是观察环境差异后选门、收集现实记忆稳定出口、躲避实体后进入安全室，或利用循环将实体引入错误层级。

## 六、问题数量与顺序

- 默认提出 4–7 个问题。
- 优先询问会改变世界关系、玩家目标、核心循环或结局的问题。
- 将紧密相关的小问题合并，不按模板字段逐项盘问。
- 已有资料足够确认的事项不再询问。
- 如果条目只剩一个关键缺口，可以只提出 1–3 个高价值问题。

## 七、用户回答后

1. 每次收到用户回答后，先把本轮所有已确认答案写入来源 JSON 与对应 Markdown；即使仍需继续提问，也不得默认暂缓写入。尚未解决的决定改写为具体 `missingItems`，确保上下文压缩或会话中断后仍能从权威文件恢复。
2. 写入时只移除已经被回答解决的 `missingItems`，不得因为阶段性写回而清空未决事项。
3. 写入后必须从更新后的来源 JSON/Markdown、之前各轮已接受答案及本轮答案重建累计确认上下文。基于全部累计内容重新审计，既检查新缺口，也复查旧答案是否仍不完整、是否与新决定冲突；不得只检查本轮或旧清单是否逐项回答。
4. 旧 `missingItems` 全部得到回答不等于条目已经完整；如果回答暴露出下一层未决事项，应把它们改写成更具体、可回答的新 `missingItems`，不得直接删除整个字段。
5. 只有重新审计后确实不存在当前成熟度所需的可执行缺口，才可以让 `missingItems` 为空；不把地图制作、音频或尚未进入当前成熟度的制作细节强行补成待补项。
6. 根据实际信息量重新判断成熟度，不因回答很长就自动升级。
7. 用户将概念定义为“无限扩展”“随时进入”或“模块化”时，只固定稳定规则和首版边界，不强迫补完所有区域。
8. 只写入真实存在或已明确要新增的引用，不伪造 ID、资源路径或实现进度。
9. 如果重新审计后仍有会改变当前成熟度设计的关键决定，在已完成本轮写回的基础上继续提出一轮聚焦问题；不得把继续提问当作不写入已确认答案的理由。
10. 如果重新审计后已没有当前成熟度所需的关键缺口，确认本轮来源 JSON 与 Markdown 已同步，不再要求用户额外发送“写入大纲”。
