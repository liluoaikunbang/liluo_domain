# 故事大纲到可玩内容转化系统

## 目标与权威来源

本系统把一个已经批准的故事节点拆成可核验的制作合同，再调用现有地图、事件、对话、玩法、素材、存档和验证能力落地。故事权威仍是 `src/game/data/story_outline/sources/*.json` 与对应 Markdown；转化报告不是第二份剧情权威，也不会批量改写节点。

## 四种模式

| 模式 | 产物 | 写入边界 |
| --- | --- | --- |
| `plan` | 引用解析、缺口、MVP、状态合同、风险与顺序 | 只读 |
| `skeleton` | 最小且 schema 有效的地图/事件/对话/测试骨架 | 仅用户指定节点 |
| `implement` | 复用现有 Skill 完成可玩主流程 | 不另建 registry/入口 |
| `validate` | 来源、路线、测试、构建、索引与人工回归结论 | 不自动修故事 |

入口命令：`npm run content:playable:plan -- --story-key <key>`。规划必须解析稳定 key、进入/完成条件、状态变化、`mapRefs/eventRefs/dialogueRefs/gameplayRefs/assetRefs/audioRefs`、失败/中断/重入与最小可玩版本。缺少的 ID 只登记缺口。

## 可玩判定

可玩内容必须能从正式入口进入，由玩家操作推进，到达明确完成点，并在需要时有真实存档合同。仅有 Markdown、地图文件、任务 UI 占位或可播放对话不算完成。第一版补齐了 Markdown frontmatter 向故事运行时合并上述生产字段的合同，但没有因此虚构任何事件或任务状态。

正式写入先经过《正式项目内容来源与版权写入门槛》。长期角色/关系变化进入独立长期记忆；需要运行时持久化时必须另走存档迁移。浏览器验证在没有 E2E 工具时明确记为人工或未运行。

## 当前示例

`world-1-glimmering-glance-campus-arrival` 已有真实校园地图引用与完整游戏大纲，但事件、对话 ID 和统一任务状态仍是缺口，因此可以生成计划，不能被报告成已可玩。
