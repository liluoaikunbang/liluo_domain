# 故事缺口发现与灵感补全系统

## 目标与适用范围

本系统从现有璃落宇宙内容中发现证据充分的结构、叙事功能、场景、角色、玩法、状态、视觉制作和题材覆盖缺口，并生成少量原创候选交用户审批。它也识别重复骨架、刻意留白和制作延期，避免把“内容少”直接等同于“必须扩写”。完整执行流程由 `liluo-story-gap-discovery` Skill 管理，只读分析由星弥（故事缺口）承担。

适用于“这个节点/系列/世界还缺什么”“补充可审批候选”“检查玩法覆盖或情节重复”“按需参考外部题材模式”。用户已经给出完整情节只需写入、既有事实查询以及代码、地图、存档、图片维护不触发。

## 三种分析模式

- 局部节点：读取目标局部关系，分析前置、过渡、过程、关系、失败/结束、余波、地图、玩法、CG 和状态；默认 3—5 个候选。
- 系列：比较中型系列的节奏、功能、场景、关系、玩法、视觉和重复结构；默认 5—8 个候选。
- 世界：先给覆盖与重复报告，再给 8—12 个最高价值方向；不一次输出几十个点子。

## 缺口分类与证据

分类包括结构、叙事功能、场景、角色、玩法、视觉制作、题材覆盖与重复冗余，完整定义见 Skill 的 `gap-taxonomy.md`。缺口证据必须指向项目路径、稳定 key 或索引记录，并核验原始文件。关键词频率、索引摘要省略或个人偏好不能单独证明缺口。

## 项目知识与外部知识

先检查项目索引，读取目标、最多两级父节点、直接子节点、最多三个相关同级节点，以及必要角色、世界规则、玩法、地图/事件/CG、反向引用和 `missingItems`。先形成项目内部的缺口假设，再决定是否查询外部知识。

外部检索支持 `off`、`light`、`deep`。能从项目事实完成时使用 `off`；需要差异化模式时默认 `light`，最多 5 张抽象卡、5 个来源摘要和 3 个短来源段落；`deep` 必须说明理由。外部内容永远是非 canon 参考。

## 候选卡、评分与排序

候选包含唯一 ID、状态、目标范围、缺口类型与证据、核心创意、故事功能、世界/角色/地点/玩法/地图/事件/CG/状态适配、与已有内容差异、外部抽象来源、六项 1—5 分、制作规模和审批选项。

`projectFit`、`gapCoverage`、`novelty`、`productionFeasibility` 越高越好；`continuityRisk`、`sourceDependenceRisk` 越高风险越大。排序综合适配、覆盖、新颖、成本、连续性和来源依赖，不因某外部模式高频就优先。

## 审批与正式写入

候选状态为 `proposed`、`accepted`、`accepted-with-changes`、`held`、`rejected`、`merged`、`expanded`、`written`。`proposed` 不得进入正式故事；接受后可交给故事撰写 Skill 展开，仍需遵守既有审批方式；`written` 必须记录真实 story key。正式写入后运行连续性、玩法、内容、索引验证，外部启发的长文本还需照搬风险检查。

## 候选存储与重复抑制

普通分析只在对话中展示。用户明确要求保存时才进入 `planning/story-gaps/`，按 active/held/approved/archived 分类；该目录不是正式故事索引。拒绝候选可保留目标和概念指纹以避免原样重荐，但一次拒绝不自动禁止整个题材。

## 原创性规则

外部知识只提取通用机制，优先综合多个来源，删除专名、独特设定、标志台词和完整顺序，并围绕璃落 canon 重做因果、环境、关系与解决方式。禁止复制、近似改写和只换人物名。正式长文本运行 `external:knowledge:copy-check`。

## 分工、示例与限制

Skill 负责范围、预算、调度、审批和下游连接；星弥只读分析并生成排序候选；主 Codex 负责用户意图、正式写入和验证。常用命令见用户命令目录，确定性合同位于 `scripts/story-gaps/`。

当前项目索引为 `partial`，需核验原文件；外部知识库虽为 `current`，抽象卡数量仍有限，light 检索可能需要少量短来源预览。候选工作台尚无独立规划索引，故不会进入正式故事检索。未来只有明确设计规划索引后才扩展。
