# 故事大纲条目模板

新增故事大纲条目，或按用户要求对已有条目进行完整重构时，Markdown 正文文件统一复制本模板。

大纲的目标不只是记录小说式剧情梗概，而是提前完成从故事到 **2D 像素冒险 RPG** 的制作拆解，使地图、探索、事件、对话、玩法、CG、像素演出、角色状态和存档变化能够直接进入后续开发。

文件必须使用 UTF-8 编码，并放置在对应世界的：

```text
src/game/data/story_outline/<世界目录>/
```

文件名统一使用：

```text
<层级编号>-<节点标题>.md
```

其中节点标题必须与来源 JSON 中的 `title` 完全一致。

本模板采用两层结构：

- **YAML**：只保存便于大纲界面检索、数据关联、状态判断和导出的结构化索引。
- **Markdown 正文**：按固定章节记录玩家实际经历、游戏画面、事件流程和制作需求，不把大段设计内容塞进 YAML。

本文件同时承担“快速大纲模板”和“完整制作规范”两种用途，但不要求所有条目从一开始就填写全部内容。实际使用时先确定成熟度：

| 成熟度 | 主要用途 | 默认要求 |
|---|---|---|
| 灵感 | 判断题材和核心玩法是否值得保留 | 只填写核心 YAML 和 5 个方向性章节 |
| 游戏大纲 | 确定玩家实际经历，供后续排期和拆分 | 填写主流程相关 YAML 和 11 个设计章节 |
| 制作设计 | 已准备进入地图、事件、对话和资源开发 | 使用完整版字段、全部相关章节和验收清单 |

条目应随内容成熟逐级补充，不要为了直接达到“制作设计”而编造尚未确定的地图、事件、CG 或资源。

## 创建时的整合顺序

每个来源 JSON 节点最终只对应一个 `src/game/data/story_outline/<世界目录>/<层级编号>-<节点标题>.md`。成熟度规则、世界候选和 `storyTags` 候选只在创建或重构时提供参考，不拆成多个运行时正文文件。

创建顺序：

1. 按本文件选择“灵感”“游戏大纲”或“制作设计”成熟度。
2. 根据 `world` 打开 `docs/系统说明/故事大纲世界选项/<世界目录>.md`。
3. 从该世界文件中选择一个主要 `storyTag`；确有跨风格需要时再增加辅助 `storyTags`。
4. 根据条目实际活动选择一个或多个 `moduleType`，并回答本文件对应的条件检查项。
5. 把已经确认的内容整合到单个正式 Markdown；候选说明、未选择选项和模板解释不得复制进正式 YAML。

## 主线任务节点不使用本模板

来源 JSON 中 `status: 主线任务` 的节点是用于组织、折叠和续接一段主线内容的容器，不是普通剧情节点，不按本模板补写地图、事件、玩法、进入条件、完成条件或制作验收内容。

当用户要求整理某个世界或某条线路的“第一个文档”“第一个节点”时，必须先查看来源 JSON 的节点状态，并跳过 `status: 主线任务` 的节点，从其后代中选择第一个普通剧情节点。不得仅按 Markdown 文件名或层级编号排序，把主线任务容器误判为第一个待整理条目。

主线任务节点只能维护其作为主线容器实际需要的标题、摘要、父子关系和展示状态。若用户明确要求整理主线总览，应使用下面的“主线备忘”结构，不得套用普通故事条目模板，也不得为了填满模板而编造玩家流程或制作引用。

### 主线备忘结构

主线备忘的用途是保存已确认的总体方向，供以后拆写对应普通剧情节点时参考。它不是“灵感”“游戏大纲”或“制作设计”的另一种成熟度，也不能因为内容较多就转用普通模板。

来源 JSON 只保留 `key`、`world`、`title`、可选 `summary`、`status`、`parentKey` 和 `order`。Markdown 的 YAML 只保留 `key`、`world`、`status`、可选 `summary`，并使用 `detailLabel: 主线备忘`；不得写入 `isTemplated`。

正文根据实际内容选择“主线定位”“已确认方向”“推荐主线阶段或展开方式”“能力、人物或主题成长参考”“前后主线衔接”“留待正式主线设计时确认”等章节，不要求为了整齐凑满。未决事项只作为将来拆写章节时的参考清单，不进入 `missingItems`。

主线任务节点不得写入 `scope`、`moduleType`、`storyTags`、`plotTags`、`bondageTags`、`specialGameplay`、`characters`、`locations`、进入条件、完成条件、状态变化、地图/事件/对话/资源引用、玩法规则、最小可玩版本或制作验收。需要这些内容时，应在主线下建立或完善对应的普通剧情节点。

### 普通剧情节点必须参考所属主线备忘

撰写主线下的普通剧情节点时，必须沿来源 JSON 的 `parentKey` 向上找到最近的相关主线任务并阅读其 Markdown；若上层主线备忘仍规定当前世界阶段、人物成长或最终方向，也必须一并参考。不能只读取当前节点和普通模板，从而把主线备忘当成孤立存档。

主线备忘中的内容按性质使用：

- “已确认方向”及确认过的前后衔接是连续性约束，下属节点默认必须遵守；需要改变时由用户明确修订主线方向，并同步更新主线备忘。
- “推荐主线阶段”“推荐展开方式”和成长参考是后续设计素材，可以在普通节点中细化或调整，但不得自动当成已经定稿的剧情事实。
- “留待正式主线设计时确认”是问题来源，只把与当前节点直接相关的事项拿来询问或登记为该节点的 `missingItems`，不得把整份主线待定清单复制给所有下属节点。
- 主线备忘不能代替普通节点自身的设计证据。普通节点仍按其真实资料判断成熟度，并独立补齐地图、事件、玩法、状态、资源与验收内容。

普通节点的正文只吸收当前真正采用的主线内容，不重复粘贴整份主线备忘。

## 缺失关键信息必须主动询问用户

创建、整理或升级普通故事条目前，必须先汇总用户本次说明、来源 JSON 节点、对应 Markdown、所属世界选项，以及项目内已经存在的地图、事件、对话、玩法、角色和资源资料。

如果现有材料不足以支撑目标成熟度，必须主动向用户指出缺口并请求补充，不得等待用户另行提醒。问题只集中在会实质改变条目的事项，包括：

- `world` 与主要 `storyTag`；
- 玩家进入位置、离开位置和核心目标；
- 地图流程、区域连接与玩家控制状态；
- 核心玩法、失败恢复与完成条件；
- 关键角色身份、对话选择和分支结果；
- 必须写入存档的状态变化；
- 已确定要使用或新增的地图、事件、对话、CG、音频和其他制作资源。

能够从项目真实资料中确认的内容必须自行查找，不重复询问用户。用户补充后，应把答案整合进正式条目；仍未解决的关键缺口应明确列出，并将条目降到现有材料能够诚实支撑的成熟度，不使用假设、通用套话或候选清单填充。

用户与整理者完成一轮讨论后，如果普通条目仍有已经确认的制作缺口，应在 YAML 中填写 `missingItems`，让故事大纲节点右下角显示“待补充”按钮。每项统一使用 `类型｜所属模块｜具体缺少内容`，例如：

```yaml
missingItems:
  - CG｜病房苏醒·梦境种子植入｜缺少植入过程与记忆闪回的正式 CG
  - 地图｜重返校园·校门口接管｜缺少校门口准确出生点配置
```

“所属模块”必须精确到本条目内的流程阶段、区域或事件，不得只写“本模块”；CG 必须说明缺少哪个模块或演出段落的 CG。只有讨论后仍真实缺失的内容才写入，补齐后立即删除对应项；`missingItems` 为空时省略字段，界面不显示按钮。主线任务容器不使用该字段。

同一条目存在多个 `storyTags` 时，列表第一项视为主要风格，后续项只追加辅助风格要求。若两个标签分别需要独立地图流程、核心矛盾和结局，应拆成两个来源 JSON 节点和两个 Markdown，而不是强行合并。

# 二、YAML 字段填写规则

## 1. 稳定节点字段

### `key`

必填。

填写来源 JSON 中全局唯一、稳定且语义明确的节点 key。

```yaml
key: world-1-glimmering-glance-dance-classroom
```

`key`同时保存在 JSON 和 Markdown 中，用于建立稳定关联。即使以后修改中文标题、文件名或层级位置，`key`也不应随意变化。

以下字段仍只由来源 JSON 管理，不重复写入 Markdown：

- `parentKey`
- `order`
- `branchLayout`

---

## 2. 原有内容索引字段

### `world`

必填，使用现有世界全名。

```yaml
world: 1-浮光掠影
```

### `storyTags`

记录该节点所属的故事栏目或内容系列。

```yaml
storyTags:
  - 诡影侵临
  - 禁域长廊
```

不要在这里填写“胶带”“职业”“追逐”等具体内容元素。

### `status`

记录节点当前展示状态，例如：

- `主线任务`
- `支线任务`
- `大纲`
- `大纲草稿`
- `灵感`
- `分类`

`status`不负责父子关系和分支布局。

### `summary`

用于大纲卡片展示的简短摘要。

应说明玩家会经历什么，不写纯文学宣传语，也不写过长背景设定。

推荐：

```yaml
summary: 璃落通过旧宿舍电梯进入过去的校园时间层，寻找荆锁会留下的求救记录。
```

不推荐：

```yaml
summary: 尘封多年的命运终于在这一夜再次转动。
```

### `detailLabel`

- 只有零散构想时使用 `灵感`
- 已按本模板完成游戏化拆解时使用 `大纲`

### `isTemplated`

用于明确标识条目是否已经按当前故事大纲模板完成整理。

- 新建条目或按用户要求完整重构的旧条目固定填写 `isTemplated: true`。
- 旧版 Markdown 未填写该字段时，运行时统一视为 `false`，界面显示“旧版未模板化”。
- 只修正错字、单字段或局部内容时，不得顺手改成 `true`；必须真正完成当前成熟度要求的 YAML 与正文章节后才能标记。
- 主线任务容器不使用该字段。

### `missingItems`

- 记录与用户讨论后仍确认缺失、且会影响后续制作的内容。
- 每项格式固定为 `类型｜所属模块｜具体缺少内容`。
- 常见类型包括 `CG`、`地图`、`事件`、`对话`、`立绘`、`音频` 和 `玩法`。
- 不得把宽泛愿望、未确认设想或可以从项目中自行查到的资料列为缺口。
- 缺口补齐后删除对应项；没有缺口时省略整个字段。

### `cgRefs`

只填写已经真实存在于图鉴或资源中的 CG 基础标题。

标题使用 CG 文件去掉扩展名和末尾差分括号后的名称。

```yaml
cgRefs:
  - 都市DID-夜班护士
```

计划制作但尚未存在的 CG 不写入 `cgRefs` 或 `cgSequence`；应在正文“CG 与关键画面”中记录需求，并同步写入 `missingItems`，注明所属模块和缺少的 CG 内容。

### `cgSequence`

记录本条目 CG 按实际播放顺序排列的具体内容，供故事节点右上角的“CG”按钮展示。每项固定使用：

```text
CG标题｜出现时机｜具体画面内容
```

```yaml
cgSequence:
  - 病房窗前苏醒｜璃落第一次恢复意识后｜璃落半坐在病床上，晨光从百叶窗切入，床边监护仪仍在闪烁
```

- 顺序必须与游戏内计划播放顺序一致；界面按列表顺序显示 `CG 1`、`CG 2`。
- `具体画面内容`必须写出角色、动作或状态、场景背景和构图重点，不能只写“关键 CG”“展示角色”等空泛说明。
- 已有真实资源的条目，其标题应与对应 `cgRefs` 基础标题一致，以便序列同时显示图鉴封面与差分入口。
- `cgSequence` 只允许收录已经存在于 `cgRefs` 且能解析到真实图鉴资源的 CG；未制作 CG 不得进入序列。
- 未制作 CG 只在正文记录设计需求，并写入 `missingItems`；制作完成、补入真实 `cgRefs` 后，才可加入 `cgSequence`。
- 同一份具体内容还必须写入正文“CG 与关键画面”，YAML 负责序列检索，正文负责完整设计；两处的标题、时机和画面内容必须一致。

### `foreshadowing`

记录本节点埋设或回收的伏笔。

### `plotTags`

记录实际出现的非紧缚题材、场景、身份与结构元素，只在节点元信息和汇总检索中展示。

```yaml
plotTags:
  - 校园
  - 时间层
  - 调查
```

### `bondageTags`

记录条目实际出现的紧缚方式或紧缚主题。该字段是故事节点卡片正文唯一直接展示的标签类型；只使用项目已有或用户明确确认的标签，不从相关情节条目自动继承。

```yaml
bondageTags:
  - DID
  - 旧式手铐
```

`storyTags` 仍是独立的故事风格大标签，不与 `plotTags` 或 `bondageTags` 合并。旧 `tags` 字段停止使用。

### `specialGameplay`

记录面向人阅读的玩法概述。

```yaml
specialGameplay:
  - 历史切片探索
  - 受限状态调查
  - 双人解结
```

该字段可以记录尚未正式注册到玩法目录中的设计。

### `characters`

记录本条目中实际出场或直接参与事件的角色。

### `requiredAbilities`

记录玩家进入或推进内容所需的能力。

例如：

```yaml
requiredAbilities:
  - 开锁
  - 异常感知
```

只有已经确定需要的能力才填写。

### `locations`

记录剧情实际涉及的世界内地点名称。

### `reference`

记录灵感来源、参考作品或类型壳。允许填写列表。

```yaml
reference:
  - 校园时间层怪谈
  - 电梯异空间题材
```

不得直接照搬参考作品的独特角色、专有设定或具体情节。

# 三、故事体量与类型字段

## `scope`

记录该节点的故事体量。

建议固定使用以下值：

- `微型事件`
- `短篇`
- `中篇`
- `主线章节`
- `大型副本`
- `长期开放模块`

示例：

```yaml
scope: 短篇
```

判断原则：

- **微型事件**：单个场景、单次交互或几分钟事件。
- **短篇**：一项核心矛盾，一至三个主要阶段，可独立结束。
- **中篇**：多个地图或多次转折，但仍围绕单一案件。
- **主线章节**：承担主要剧情推进并向多个后续节点输出状态。
- **大型副本**：拥有多个区域、独立玩法循环和阶段性目标。
- **长期开放模块**：能够反复进入，有稳定的经营、收集或任务生成结构。

不能仅因为题材宏大就标记为大型副本。应根据玩家实际流程和制作体量判断。

---

## `moduleType`

记录玩家主要进行的游戏活动，允许使用列表。

推荐类型包括：

- 探索
- 解谜
- 潜行
- 追逐
- 脱困
- 战斗
- 经营
- 职业体验
- 生存
- 护送
- 调查
- 互动小说
- 小游戏
- 综合

示例：

```yaml
moduleType:
  - 探索
  - 调查
  - 脱困
```

`moduleType` 不对应独立模板文件。一个条目可以选择多个类型，并在同一个“玩法设计”章节中回答对应问题：

| moduleType | 需要重点回答的问题 |
|---|---|
| 探索 | 地图如何连接、哪些物件可调查、道路如何解锁、再次返回有什么变化 |
| 调查 | 证据从哪里获得、是否有调查顺序、错误判断如何反馈、结论怎样写入状态 |
| 解谜 | 规则与提示是什么、玩家输入什么、怎样判断成功、失败后如何重置 |
| 潜行 | 敌人视野与巡逻如何工作、躲藏点在哪里、暴露后进入追逐还是重置 |
| 追逐 | 起点和终点、追逐者规则、路线变化、失败恢复点和紧张反馈 |
| 脱困 | 初始限制、玩家仍可进行的操作、解除步骤、失败反馈和解除后的状态恢复 |
| 战斗 | 敌人配置、场地规则、胜负条件、奖励、失败恢复和战后地图变化 |
| 经营 | 核心循环、资源来源与消耗、阶段目标、离线或重复进入规则 |
| 职业体验 | 职业任务循环、工作场所、NPC需求、异常事件如何打断日常流程 |
| 生存 | 持续压力来源、补给、时间或波次目标、失败损失和撤离方式 |
| 护送 | 护送对象行为、路线选择、保护失败条件、途中事件和终点状态 |
| 互动小说 | 从地图何处进入、选择分支、状态后果、如何返回地图主流程 |
| 小游戏 | 操作、规则、计分或成功条件、重试方式、奖励以及是否可跳过 |
| 综合 | 明确一个核心类型，其余只作为辅助，避免把多种玩法等量堆叠 |

---

## `estimatedPlaytime`

记录预计首次通关时长。

```yaml
estimatedPlaytime: 30-45分钟
```

流程尚未完成或无法合理估算时留空，不制造假精度。

---

## `contentWarnings`

用于玩家进入前提示、平台版本管理和内容筛选。

```yaml
contentWarnings:
  - 绑架
  - 强制身体束缚
  - 封闭空间
```

`contentWarnings`与两类内容标签作用不同：

- `plotTags`用于非紧缚情节分类和检索；
- `bondageTags`用于紧缚方式与紧缚主题分类，并在节点卡片展示；
- `contentWarnings`用于玩家提示和版本控制。

# 四、游戏制作关联字段

## `mapRefs`

填写计划复用或已经建立的地图 `mapId`。

尚未建立地图注册项时留空，不编造 ID。

## `eventRefs`

填写地图 `events.json` 或公共事件中已存在或已经明确要新增的稳定事件 key。

建议统一命名为：

```text
<世界缩写>.<模块key>.<事件用途>
```

例如：

```yaml
eventRefs:
  - modern.jingsuo-elevator.enter-old-floor
  - modern.jingsuo-elevator.collect-old-phone
  - modern.jingsuo-elevator.return-present
```

禁止使用：

```text
event1
event2
new-event
```

稳定 key 应满足：

- 只使用小写英文、数字、连字符和点号；
- 不随中文标题润色而改变；
- 同一模块使用统一前缀；
- 名称能看出触发内容或作用。

## `dialogueRefs`

填写已存在或已经明确要新增的稳定对话 key。

```yaml
dialogueRefs:
  - modern.jingsuo-elevator.teacher-warning
  - modern.jingsuo-elevator.student-rescue
```

## `gameplayRefs`

记录本条目的主要玩法，可以填写多个。只填写：

```text
src/game/data/gameplay_outline/catalog.json
```

中已经存在的玩法 ID。

```yaml
gameplayRefs:
  - gameplay-001
  - gameplay-044
```

填写前必须先检索玩法总表，按玩法的正式名称选择最接近本条目主要操作循环的条目，不得仅凭印象编写 ID，也不得在这里填写尚不存在的玩法编号。

如果玩法总表中没有需要的玩法：

1. 先确认现有玩法的变体是否已经能够覆盖需求，避免只因剧情包装不同而重复建玩法。
2. 确认确属新的操作循环后，在 `src/game/data/gameplay_outline/catalog.json` 中创建正式玩法条目，补齐唯一 `id`、连续编号、玩法名称、所属分类、摘要、表现模式和必要变体。
3. 新玩法必须纳入玩法栏目现有分类、检索、统计和 JSON 导出，不能只在故事 Markdown 中孤立记录。
4. 新玩法进入玩法总表并通过玩法目录校验后，再把其 ID 写入本条目的 `gameplayRefs`。

故事栏“汇总”的“主要玩法”列会根据 `gameplayRefs` 自动解析玩法总表中的正式名称。失效 ID 不参与汇总，因此新增或改名玩法时必须保持目录与引用同步。

区别如下：

- `specialGameplay`：人类可读的本章特殊规则、限制或玩法变体，不代替主要玩法名称。
- `gameplayRefs`：主要玩法的唯一结构化来源；界面、关联弹窗和故事汇总均从玩法总表解析正式名称。

## `assetRefs`

只填写已经确定使用的项目相对路径。

统一要求：

- 使用项目根目录相对路径；
- 使用正斜杠 `/`；
- 不填写本地绝对路径；
- 不使用 Windows 反斜杠；
- 不把计划制作的文件伪装成已有资源。

示例：

```yaml
assetRefs:
  - src/assets/game/cg/modern/urban_did_nurse.png
```

## `audioRefs`

填写已经存在或明确确定使用的音乐、环境音、语音和音效 key 或路径。

未确定时留空。

# 五、条件与状态字段

## `entryConditions`

记录进入该条目的任务、道具、角色状态、时间、地点或前置事件条件。

```yaml
entryConditions:
  - 已完成舞蹈教室异常事件
  - 已获得荆锁会旧挂件
```

每条条件应能转换为存档字段或事件判断。

## `completionConditions`

必须填写可转化为程序判断的明确条件，不能只写“剧情结束”或“璃落成功脱困”。

推荐：

```yaml
completionConditions:
  - 已调查旧宿舍床架
  - 已取得未发送的求救录音
  - 已触发电梯返回事件
  - 已与现任教师完成结尾对话
```

## `stateChanges`

记录完成、失败或重要选择后需要写入存档的变化。

```yaml
stateChanges:
  - 标记封寝夜时间层已完成
  - 获得旧手机录音
  - 解锁转送日电梯按钮
  - 更新年长教师后续对话
```

应描述具体改变，不写模糊结论。

# 六、正文章节填写规则

## 1. 模块定位与体验目标

说明本条目在整个游戏中的作用，以及玩家通过哪些操作获得什么体验。

不要只写抽象主题。

不推荐：

> 表现过去学生的孤独。

推荐：

> 玩家需要独自在封闭宿舍中调查床架、储物柜和旧手机，在无法正常使用双手的状态下寻找求救证据，通过受限移动和环境声音感受到当年学生无法离开的处境。

---

## 2. 故事体量与核心差异

必须说明：

- 本条目属于微型事件、短篇、中篇还是主线章节；
- 预计使用多少个主要地图或区域；
- 本条目的核心矛盾是什么；
- 与已有相似事件最关键的区别是什么；
- 哪一项核心机制原则上只在本条使用。

例如：

> 本条为短篇时间层探索，只使用旧宿舍一层和电梯前室两个区域。核心机制是玩家被固定在铁架床附近后，通过有限移动调查周围物品。它与普通绑架脱困的区别在于，目标不是寻找工具逃跑，而是恢复当年未能发出的求救信息。

该章节用于避免“只换地图，不换故事结构”。

---

## 3. 玩家进入与离开

### 进入条件

记录实际进入节点所需条件。

### 初始位置与初始状态

至少说明：

- 玩家出生地图；
- 出生坐标或区域；
- 初始朝向；
- 初始服装或身体状态；
- 是否允许自由移动；
- 同行角色位置。

### 完成条件

与 YAML 中的 `completionConditions`一致，但正文可以解释条件之间的关系。

### 失败、中断与返回

说明：

- 是否允许失败；
- 失败后从哪里恢复；
- 中途离开后是否重置；
- 再次返回时哪些事件不重复；
- 是否存在永久错过内容。

---

## 4. 游戏流程

按玩家实际操作顺序拆分阶段。

每个阶段至少填写：

1. 玩家当前目标；
2. 所在地图或界面；
3. 必须完成的交互；
4. 触发的事件或演出；
5. 玩家状态变化；
6. 阶段结束条件。

不能只按小说章节概括剧情。

推荐格式：

```markdown
### 阶段一：进入旧宿舍

- 玩家目标：
- 所在区域：
- 必须交互：
- 自动事件：
- 状态变化：
- 阶段结束条件：
```

---

## 5. 地图与探索设计

### 地图区域与连接

记录：

- 出生点和出口；
- 区域之间的连接方式；
- 电梯、楼梯、门、暗道和传送点；
- 哪些区域首轮封锁；
- 哪些区域完成事件后开放。

### 可调查物与环境互动

记录所有具有剧情、玩法或反馈作用的物件。

不要罗列纯装饰物。

### 道路限制与状态限制

说明：

- 哪些道路需要能力、道具或任务状态；
- 身体受限时哪些通道无法通过；
- 是否需要侧身、爬行、跳跃或特殊移动；
- NPC是否会因玩家状态改变反应。

### 场景氛围与环境变化

记录：

- 昼夜；
- 天气；
- 灯光；
- 雾气；
- 停电；
- 门窗封锁；
- 环境破坏；
- 时间层切换；
- 事件前后地图变化。

---

## 6. 角色与 NPC 安排

记录每名角色：

- 所在阶段；
- 地图位置；
- 初始朝向；
- 巡逻或移动路线；
- 可交互时机；
- 对玩家身体状态的反应；
- 事件前后的外观和行为变化；
- 是否会离开、跟随或阻挡道路。

不要只写角色心理活动。

---

## 7. 事件与状态变化

事件统一使用：

```text
触发条件 → 演出或交互 → 结果 → 状态写入
```

明确区分：

- 自动事件
- 区域触发事件
- 调查事件
- 对话事件
- 一次性事件
- 可重复事件
- 条件分支事件
- 失败事件

---

## 8. 玩家控制状态

涉及身体束缚、负伤、变装、押送、封闭设备或其他控制变化时，必须填写玩家控制状态。

推荐使用表格：

| 状态阶段 | 移动 | 奔跑 | 调查 | 使用道具 | 开门 | 对话 | 地图表现 | 解除条件 |
|---|---|---|---|---|---|---|---|---|
| 正常状态 | 正常 | 可用 | 全部可用 | 可用 | 可用 | 正常 | 普通行走图 | 触发异常 |
| 双手受限 | 正常或减速 | 受限 | 部分可用 | 禁止手持道具 | 部分门不可开 | 正常 | 受限行走图 | 找到解除方法 |
| 固定状态 | 禁止 | 禁止 | 仅附近调查 | 禁止 | 禁止 | 可用 | 地图定点演出 | 完成环境互动 |

还应说明：

- 是否切换专用行走图；
- 是否需要爬行、跳动或侧身动画；
- 是否改变碰撞箱；
- 是否改变移动速度；
- 是否禁用菜单、装备或快捷道具；
- NPC是否能够牵引、搬运或推动玩家；
- 状态解除后是否恢复原装备和位置。

---

## 9. 玩法设计

### 主要玩法

按照 YAML `gameplayRefs` 的顺序逐项填写，可以有多个。每项标题必须使用玩法总表中的正式玩法名，并至少说明：

- 对应的 `gameplayRefs` ID；
- 在本条目哪个流程阶段出现；
- 玩家实际执行的操作循环；
- 本条目采用了哪些既有玩法变体；
- 为剧情、地图或角色状态做了哪些具体调整；
- 成功、失败和退出后如何回到故事流程。

```markdown
### 主要玩法

#### 房间式地牢探索（gameplay-001）

- 使用阶段：地下设施调查阶段。
- 操作循环：进入房间、调查机关、解除封锁、选择出口。
- 本条调整：角色双手受限时不能使用普通开关，需要借助环境物件触发。
```

正文中的主要玩法名称和顺序必须与 `gameplayRefs` 解析结果一致，不能另写玩法总表中不存在的简称或临时名称。

### 辅助玩法

记录不承担主流程、但增强体验的玩法。

### 成功条件、失败条件与反馈

说明：

- 玩家怎样判断自己做对了；
- 错误操作有什么即时反馈；
- 是否可以重试；
- 奖励是什么；
- 是否有重复游玩价值。

新玩法若尚未进入玩法总表，必须先补建并纳入玩法栏目完整汇总，再回填 `gameplayRefs` 和本节正文；不能直接编造引用，也不能让玩法只存在于单篇故事大纲中。

---

## 10. 对话与玩家选择

记录：

- 对话地点；
- 触发方式；
- 参与角色；
- 主要信息；
- 选择项；
- 条件分支；
- 状态后果；
- 是否进入互动小说模式。

大量文字分支只在确有必要时进入互动小说模式，避免整个模块无条件变成纯 GalGame。

---

## 11. CG 与关键画面

正文按 `cgSequence` 的顺序逐张建立三级标题，并完整写出具体画面。例如：

```markdown
### CG 1：病房窗前苏醒

- 出现时机：璃落第一次恢复意识后。
- 具体画面：璃落半坐在病床上，晨光从百叶窗切入，床边监护仪仍在闪烁。
```

每张 CG 至少说明：

- 触发时机；
- 画面主体；
- 角色身体状态；
- 场景背景；
- 构图重点；
- 是否存在差分；
- 播放前后玩家状态；
- 播放后返回地图、进入对话还是切换下一事件。

已有真实资源才写入 YAML 的 `cgRefs`；确认会在本条目播放后，再按顺序写入 `cgSequence`。

尚未制作的 CG 只在正文写需求，并同步写入 `missingItems`；不得写入 `cgRefs` 或 `cgSequence`。

无束缚、轻度束缚和加固差分不必强行按连续剧情顺序使用，也可以分别承担：

- 职业展示；
- 事件前状态；
- 关键画面；
- 图鉴独立收藏；
- 可选分支差分。

---

## 12. 像素演出与镜头

记录：

- 角色走位；
- 转身；
- 停顿；
- 表情或立绘切换；
- NPC包围、牵引或押送；
- 地图物件变化；
- 镜头跟随；
- 镜头锁定；
- 平移；
- 缩放；
- 淡入淡出；
- 屏幕震动；
- 遮罩；
- 时间层切换；
- CG前后的衔接。

优先使用地图内像素演出表达行动。CG和长文本只承担像素画面难以清楚表现的关键瞬间。

---

## 13. 美术、音频与特效资源

按以下类别记录：

- 地图图块；
- 场景物件；
- 角色行走图；
- 状态行走图；
- 立绘；
- CG；
- UI；
- 音乐；
- 环境音；
- 动作音效；
- 语音；
- 特效。

正文中可以区分：

- 已有可复用；
- 需要新增；
- 尚未确认。

但“尚未确认”的资源不得填写进 YAML 路径。

---

## 14. 隐藏内容、收集与重复探索

可以记录：

- 可选调查；
- 隐藏路线；
- 收集物；
- 二次返回变化；
- 不同状态下的新对话；
- 可重复小游戏；
- 特殊CG条件。

没有明确设计时留空，不为填满模板强行增加收集系统。

---

## 15. 前后章节与世界状态衔接

说明：

- 前置节点提供了什么状态；
- 本条目接收哪些伏笔；
- 本条目向后续输出什么状态；
- 哪些角色关系发生改变；
- 哪些地图可以再次访问；
- 哪些物品、记录或能力进入长期存档；
- 哪些异常或道路永久关闭。

这里只描述内容连接，不修改来源 JSON 的父子关系。

---

## 16. 最小可玩版本

列出第一次落地时不可缺少的内容。

至少应包括：

- 一条能够从进入走到完成的主流程；
- 必要地图或临时地图；
- 必要事件；
- 必要对话；
- 核心玩法；
- 必要玩家状态；
- 完成后的状态保存；
- 正常离开方式。

不要把所有CG、隐藏路线、复杂差分和额外小游戏都设为首版阻塞项。

---

## 17. 后续扩展

只记录主流程可玩后再补充的内容，例如：

- 可选对话；
- CG差分；
- 隐藏证据；
- 额外NPC反应；
- 二周目变化；
- 高难度脱困；
- 更复杂的像素演出；
- 玩法变体。

不得使用“以后可以不断增加更多事件”这类无边界描述。

确实需要长期扩展时，必须列明：

- 预计增加哪些具体内容；
- 每项新增内容与现有内容有什么差异；
- 新内容的结束条件；
- 是否需要拆成新的独立节点。

---

## 18. 制作验收清单

使用可核对的复选项。

```markdown
- [ ] 来源 JSON 节点 key 与 Markdown key 一致
```

# 七、短篇防膨胀与防换皮规则

## 短篇默认边界

普通都市事件、职业体验和单次绑架支线，默认控制为：

- 一个主要职业或场所；
- 一个核心矛盾；
- 一种主要进入方式；
- 一次明确受困；
- 一种独有的应对或脱困方式；
- 一个完整结局；
- 一至三个主要地图区域；
- 一至两个主要玩法。

不因为拥有多张CG就强行扩展成多阶段长篇。

## 禁止模糊扩展

不写：

- 后续又出现了更多异常；
- 之后不断有新的受害者；
- 璃落以后还会反复执行类似任务；
- 系统继续生成更复杂的规则；
- 城市中还有很多相同地点。

需要扩展时，必须具体写明：

- 新增事件名称；
- 进入方式；
- 独有机制；
- 与旧事件的差异；
- 结局；
- 是否拆成独立节点。

## 防止换皮复用

新增条目必须说明与已有相似节点的核心区别。

不仅更换：

- 城市；
- 职业；
- 制服；
- 绑架地点；
- 束缚道具。

还应至少改变其中一项：

- 玩家目标；
- 事件结构；
- 绑架者目的；
- 地图探索方式；
- 玩家控制状态；
- 求救或脱困方式；
- NPC关系；
- 结局结果；
- 核心玩法。

例如，外卖员与超市售货员即使都遭遇普通绑架，也不能都写成：

> 发现犯罪后被捆进仓库，通过制造声音引来保安。

两者应采用不同的调查和脱困结构。

# 八、不同成熟度的最低要求

成熟度描述的是设计完成程度，不等同于故事体量。短篇也可以进入制作设计；大型副本在早期也可能仍只是灵感。

## 一级：灵感

适用于判断题材、核心冲突和玩法方向是否值得保留。

最低 YAML：

- `key`
- `world`
- `status`
- `summary`
- `detailLabel: 灵感`
- `isTemplated: true`
- `scope`
- `moduleType`
- 已经确定的 `storyTags`、`plotTags`、`bondageTags`、`characters`、`locations` 或 `reference`

最低正文：

- 模块定位与体验目标；
- 故事体量与核心差异；
- 游戏流程；
- 地图与探索设计；
- 玩法设计。

这一阶段允许只写方向和关键差异，不要求事件 key、资源路径、精确完成条件或制作验收项。未知内容直接省略或留空。

## 二级：游戏大纲

适用于确认玩家从进入到完成会实际经历什么，内容应足以判断地图数量、玩法结构和制作规模。

最低 YAML：

- 灵感阶段的全部核心字段；
- `entryConditions`
- `completionConditions`
- `stateChanges`
- 已经确定的 `cgRefs`、`cgSequence`、`gameplayRefs`、`foreshadowing`、`specialGameplay`、`requiredAbilities`；讨论后仍存在制作缺口时填写 `missingItems`；
- 已真实存在的 `mapRefs`、`gameplayRefs`；尚未注册的引用仍留空。

最低正文：

- 模块定位与体验目标；
- 故事体量与核心差异；
- 玩家进入与离开；
- 游戏流程；
- 地图与探索设计；
- 角色与 NPC 安排；
- 事件与状态变化；
- 玩法设计；
- 对话与玩家选择；
- 前后章节与世界状态衔接；
- 最小可玩版本。

涉及身体限制或操作变化时，必须同时填写“玩家控制状态”；存在计划中的关键画面时填写“CG 与关键画面”。其他制作型章节可以等到真正排入开发后再补。

## 三级：制作设计

适用于已经准备进入 Phaser 地图、事件、对话、素材和存档实现的条目。

要求：

- 使用“完整版制作模板”的全部 YAML 字段，未知值留空，不编造引用；
- 保留并填写全部与本条实际相关的正文章节；
- 明确地图与区域连接、事件触发链、对话分支、玩家控制状态、CG 时机、像素演出和资源需求；
- 给出可独立落地的最小可玩版本；
- 完成可逐项核对的制作验收清单。

只有小说式情节、人物心理、长篇对白或文学化场景描述，却没有玩家操作、地图流程、事件触发、状态变化和完成条件的内容，最多只能处于灵感阶段，不能标为可制作的游戏大纲。

## 故事体量的默认成熟度

- `微型事件`、`短篇`：新增时默认至少达到“游戏大纲”；只有用户明确要求立即制作时才补到“制作设计”。
- `中篇`、`主线章节`、`大型副本`、`长期开放模块`：可以先以灵感立项，但在确定进入开发前必须先达到“游戏大纲”，排入实际制作时再达到“制作设计”。
- 任何体量只要已经开始编写地图、事件、对话或资源代码，就必须同步补到“制作设计”。

模板升级应逐级补充，不应因为条目体量较小就省略主流程，也不应因为题材宏大就在灵感阶段填写大量虚假的制作细节。

# 九、来源 JSON 最小结构

```json
{
  "key": "全局唯一且语义清晰的节点-key",
  "world": "与 Markdown 的 world 一致",
  "title": "与 Markdown 文件标题一致",
  "status": "大纲",
  "parentKey": "直接前序节点的 key",
  "order": 10
}
```

Markdown 中的 `key`、`world`、`status`必须与 JSON 对应字段保持一致。

# 十、默认连接规则

除非用户明确说明新条目属于哪个节点的 `side`，否则新增条目一律不创建分叉，也不设置：

```json
"branchLayout": "side"
```

当用户要求在 `A` 下方加入 `B`，且原链为：

```text
A → C
```

必须改为：

```text
A → B → C
```

具体处理：

```text
B.parentKey = A.key
C.parentKey = B.key
```

不得保留 `A → C` 的同时再增加 `A → B`，否则会形成未经授权的分叉。

如果目标节点已经拥有多个直接子节点，而用户没有说明：

- 插入哪条链；
- 是否属于 side；
- 哪个原后继需要后移；

不得自行猜测，应先确认插入位置。

修改前后必须核对：

- 节点 key 总数；
- 唯一 key 数量；
- 是否存在重复 key；
- 是否存在缺失或无效 `parentKey`；
- 用户指定节点是否仍然存在；
- 原有后续节点是否仍然存在；
- 插入后的链路是否符合预期；
- 是否意外产生多个普通直接子节点。

# 十一、兼容与迁移规则

- 模板升级不要求一次性重写所有已有 Markdown。
- 新增条目必须使用新版模板体系，并按当前成熟度选择最低字段和章节；只有进入制作设计阶段才使用完整版。
- 新增或完整重构后的普通条目必须填写 `isTemplated: true`；没有该字段的旧条目继续按“旧版未模板化”显示，不批量猜测迁移状态。
- 修改已有条目时，如果只是错字、单字段或局部内容调整，不强制重构整篇。
- 用户明确要求“完善大纲”“改成游戏大纲”“按模板重构”或进行大范围正文修改时，才将对应条目升级为新版结构。
- 默认只升级用户明确指定的条目。
- 不连带重构其父节点、子节点或同级节点。
- Markdown升级不得擅自修改来源JSON的父子关系。
- 重命名标题时必须同步修改文件名和JSON中的`title`，但稳定`key`原则上保持不变。
