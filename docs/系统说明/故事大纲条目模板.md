# 故事大纲条目模板

新增故事大纲条目时，Markdown 正文文件统一复制下面的模板。文件必须使用 UTF-8 编码，并放在对应世界的 `src/game/data/story_outline/<世界目录>/` 下。文件名使用 `<层级编号>-<节点标题>.md`，其中节点标题必须与来源 JSON 中的 `title` 一致。

```markdown
---
world: 
storyTags:
status: 大纲
summary: 
detailLabel: 灵感
cgRefs:
foreshadowing:
tags:
specialGameplay:
characters:
requiredAbilities:
locations:
reference: 
---

在这里填写条目正文。
```

字段填写规则：

- `world`：必填，使用现有世界全名，例如 `3-尘寰问道`。
- `storyTags`：所属故事标签；有多个值时使用 YAML 列表。
- `status`：节点展示状态，例如 `主线任务`、`大纲`、`大纲草稿` 或 `灵感`；不负责父子关系和 side 布局。
- `summary`：用于大纲卡片的简短摘要。
- `detailLabel`：详情按钮名称；默认使用 `灵感`，明确为完整大纲时可以使用 `大纲`。
- `cgRefs`：关联图鉴 CG 的基础标题列表；标题使用 CG 文件去掉扩展名和末尾差分括号后的名称。
- `foreshadowing`：伏笔列表。
- `tags`：内容标签列表。
- `specialGameplay`：特殊玩法列表。
- `characters`：相关角色列表。
- `requiredAbilities`：需要的能力列表。
- `locations`：相关地点列表。
- `reference`：灵感来源或参考作品。
- 暂无内容的字段保留为空，不填写假数据，也不要写“无”“待定”等占位结果。
- 列表字段有内容时按下面的格式填写：

```yaml
storyTags:
  - 标签一
  - 标签二
cgRefs:
  - 都市DID-KTV服务员
```

来源 JSON 中的节点至少包含以下结构：

```json
{
  "key": "全局唯一且语义清晰的节点-key",
  "world": "与 Markdown 的 world 一致",
  "title": "与 Markdown 文件标题一致",
  "status": "大纲",
  "parentKey": "直接前序节点的 key",
  "order": 10
}
```

## 默认连接规则

除非用户明确说明新条目属于哪个节点的 `side`，否则新增条目一律不创建分叉，也不设置 `branchLayout: "side"`。

当用户要求在 `A` 下方加入 `B`，且原链为 `A → C` 时，必须改成：

```text
A → B → C
```

具体做法是让 `B.parentKey = A.key`，再把原直接后继 `C.parentKey` 改为 `B.key`。不得保留 `A → C` 的同时再增加 `A → B`，否则会形成未经用户授权的分叉。

如果目标节点已经有多个直接子节点，而用户没有说明要插入哪条链或属于哪个 `side`，不得自行猜测，应先向用户确认。

修改前后必须核对：

- 节点 key 总数与唯一 key 数量。
- 是否存在重复 key 或缺失的 `parentKey`。
- 用户指定节点及其原有后续节点是否仍然存在。
- 从插入点开始的链路是否符合预期。
- 是否意外产生多个普通直接子节点。
