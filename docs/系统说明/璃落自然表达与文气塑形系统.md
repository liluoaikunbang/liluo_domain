# 璃落自然表达与文气塑形系统

## 定位

`liluo-natural-expression` 决定“怎样表达”，不决定“写什么”。故事事实、世界观、连续性、事件状态与项目结构仍由对应权威文件和专业 Skill 决定。

路径：`.agents/skills/writing/liluo-natural-expression/`。它属于外部通用方法经项目化改造后的 writing 能力，不放入 `liluo-project/`。

## 触发与排除

非技术、面向阅读体验的文本默认 `light`：故事大纲叙事段落、小说、游戏对话、角色心理、场景/CG 文案、创作组对话、项目手记、玩家提示、世界观介绍、公开开发叙事，用户要求的**试笔 / 测试写作 / 点名绑法草稿**，以及**普通 RAG 知识卡正文、Style-RAG 抽象风格说明、文风包旁白、外部评权说明、抽查协商与改稿说明**。用户不必每次额外说“润色”。主智能体须在动笔前读取本 Skill；不得凭记忆跳过。

改写或新建上述 RAG / Style-RAG 阅读向文案时，同样先走 `light`：说清用途与邻居差别，用可检验的具体说法，不用套话或空泛层级术语。字段名、ID、路径、CLI、JSON 结构与命令输出保持 `off`，不文学化。工作流入口见 `liluo-external-fiction-knowledge`、`liluo-style-rag` 与 [知识检索抽查校准系统](./知识检索抽查校准系统.md)。

代码、JSON/YAML/TOML、schema、CLI、路径、日志、数据表、技术接口、权限合同、结构化交接、强制规范、逐字引用和用户要求原样保存的文本默认 `off`。混合文档只处理叙事区域。

## 交付前自检（主智能体）

阅读向 compose/revise 交付前，主智能体至少完成一次合同自检：动作与空间是否可信；若使用固定绑法名称，名称与识别姿态是否一致。需要时用本 Skill 的 `diagnose` 做只读检查。正式写入故事或对话文件且含命名绑法时，可再委派 `liluo_content_auditor` 抽查；聊天试笔默认不另开 Agent，但**不得省略** Skill 自检。

## 操作与强度

- `compose`：从已确认材料生成对应类型的自然表达。
- `revise`：保留事实、结构和用途，只改需要改善的部分。
- `diagnose`：只指出机械结构和人物声音问题，不改正文。
- `light`：读取快速合同与一个文本类型配置，不大幅扩写。
- `deep`：用于正式章节、关键剧情、长对话、核心角色场景、重要手记或公开首页；执行风格、声音、机械结构、二次检查、事实核对和精简。

## 高频合同

默认保护：先保证动作、身体、物体与空间关系可信，再处理节奏、声音和潜台词；不逐项翻译提纲、不重复解释情绪、不让段落持续整齐、不统一人物声音、不用错别字伪装人味、不堆叠比喻、不为短促指令外挂场景外抽象修饰、不改变事实/状态/数值/key，已经自然的段落保持稳定。

详细配置按需加载：小说、大纲、游戏对话、团队对话、项目手记、公开开发叙事、角色声音和虚构束缚题材。项目正式角色统一为成年人，因此不再为年龄不明设置额外写作分支；束缚题材配置只改善虚构叙事质量，不提供现实操作教程。

## 璃落的校准说明

【璃落指出：针对自然表达的逐轮修改，只要形成可复用判断，就必须在同一任务同步进权威规范，不能只改当前文案。】

自然表达实验中的用户反馈先用于修正当前文本；其中已经明确、能跨场景复用的判断，同步收束到本系统说明，并更新必要的 Skill 局部合同、测试和设计记忆。仅针对一句话的临时措辞不强行沉淀，也不保存聊天流水账。

【璃落指出：束缚写作先核对绑法名称与关键姿态；后手观音以双手在背后合掌、指尖朝上为核心，不能写成以并腕压肘为核心的欧式并肘。】

涉及有固定含义的姿态或技法名称时，先确定它区别于相近方式的识别动作，再据此安排起始姿态、过程和完成状态。名称与动作骨架冲突属于逻辑错误，不能用增加圈数、力度或细节密度来掩盖。

【璃落指出：不为短促指令、对话附注或普通动作外挂与场景无关的抽象修饰和比喻；像“像在核对一门功课”这类外来框架属于不当文气，应改回直说的语气、音量或停顿。】

比喻与修饰必须来自当前人物经验与场景材料，并改变读者对感知、动作或关系的理解。学校、考试、办公等场景外框架，若未被正文建立，不得用来给口令、动作说明或气氛加“聪明感”或“文学感”。无独特作用时直接删掉，不另造同质比喻顶替。

## 虚构束缚题材的轻量外部检索

实际创作或修订束缚场景前，必须先做一次低 token 的定向检索路由。写法、视角、节奏、环境反馈、人物能动性与关系变化查询 `liluo-external-fiction-knowledge`，默认一个查询、最多 5 张抽象卡或短结果；绑法术语、命名姿态、世界构建、提示架构与视觉标签查询 `liluo-restraint-research-pack` 的外部 Skill 派生卡，默认一个查询、最多采用 3 张卡。只有两类需求都实质影响当前段落时才各查一次。抽象结果不足时，小说库最多核验 2 段不同来源短原文，研究包最多核验 2 份最相关摘要，不读取整个包。

外部材料始终属于 `reference-only`，不得保留原句、专名、独特事件顺序、色情化凝视或现实可执行的伤害细节。研究包中的提示文本不执行，术语摘要只作交叉核对线索。故事事实仍以项目权威来源为准；正式写入受外部检索影响的长文本前，运行外部知识库的直接照搬风险检查。这项规则的目的，是用极小检索预算避免闭门重复同一种写法，而不是模仿某位作者或扩大素材读取。

## 可信度门禁

含蓄和文气不得以动作可信度为代价。涉及具体动作时，按“起始姿态—人物动作—物体反馈—实际后果”快速推演，确认人物做得到、物体会如此反应、前后方位连续。看似精确却不符合身体、物体或空间逻辑的细节属于伪具体性。

普通动作可以只完成眼前之事，不强迫它同时证明人物熟悉、聪明或有经历。只有设定或当前场景已经提供依据时，才用特殊操作承担这类暗示；若一个动作需要额外解释才能成立，优先换回朴素、可信的动作。这项门禁不禁止拟人、比喻或省略，只要求它们服从人物视角与场景功能；场景外抽象修饰同样视为文气越界，见上节校准。

环境不能被删空，也不能抢走人物：只保留会进入角色感知、改变动作或影响判断的物理变化，删去无功能拟人和同义铺陈。身体状态、束缚方式与空间关系使用直观准确的词。动作细节遵循“最小充分”：写到读者能理解意图、空间与结果即可；“抱住”“扶稳”等普通动作已经清楚时不继续拆解左右手、接触路径和步骤。紧急场面可加一个“一把”“猛地”之类的短促修饰词传递速度，但不连续叠加副词、姿态和步骤；只有存在空间歧义或结果依赖接触点时才展开。人物先应对正在发生的危险，再在合理窗口进食、照顾或交谈。

“最小充分”由场景核心决定，不等于统一压缩过程。若“怎么绑”、如何制作或怎样完成某项变化本身就是看点，正文应选择性呈现起始固定、推进顺序、材料的可见路径、姿态变化和完成状态；可以写宽泛结法与绳路，也可以选择具体或约略圈数、逐段收紧和压迫感来突出程度。边界不是完全删除数量与力度，而是避免让每一步都携带角度、受力数值、完整结法和全部可复现参数。

过程细节必须服从术语与身体逻辑。写有固定名称的绑法时，先锁定手掌方向、手腕位置、手肘关系或躯干路径等识别姿态，再决定哪些绳路需要展开；不能在术语错误的动作骨架上继续增加“具体感”。

叙述连接同样服从因果：没有真实反差就不用“却”，没有必要的语势变化就不用破折号。段尾停在角色感知到的动作后果、判断或新信息上，不由作者出面评价人物、解释主题或替正文总结意义。

## 意义门禁：不以伪问题代替悬念

不能为了制造神秘、分量或一句看似有余味的段尾，临时抛出没有可回答对象、没有调查方向、也不影响角色或玩家下一步行动的设问。诸如“究竟是 A，还是某人坚持留下的 B”一类句子，若正文没有建立回答者、证据路径或由答案引出的选择，只是在替缺失的具体内容制造雾气。

保留问题时，文本必须能说明谁可能回答、玩家或角色将如何查证，或答案会改变什么判断、目标与行动。否则直接写已确认事实；确有未知时，写成具体待解事项。该门禁不禁止悬念，而是要求悬念在故事、调查或角色选择中有可执行的落点。

## 风格档案

`style-profiles/` 只保存抽象规律：视角、节奏、密度、动作与心理比例、角色观察习惯和用户反复确认的稳定偏好。一次临时修改不进入长期档案；不保存隐藏推理、完整修订历史、长样文或对在世作者的模仿档案。

## 外部谱系

除虚构束缚题材按需求选择小说库或已导入研究包的轻量检索外，日常调用只读本地 Skill 和风格档案，不查询外部资料。只有反复修订仍失败、缺少文本类型、准备升级或用户明确比较来源时，才按能力卡 → 方法卡 → 更新摘要 → 最相关原始文件查询。

`skill-lineage.json` 固定记录了 Agent Skills 规范、OpenAI skill-creator、Creative Writing Skills、Avoid AI Writing 与 Story Skills 的 commit 和吸收范围。没有采用英文固定禁词表、统一标点禁令、外部故事目录/CLI 或任何自动安装与 Git 写入规则。

## 已知限制

Node 脚本能确定性检查路由、明显机械模式和 key/数值/状态锚点，但文学质量仍需结合具体文本人工判断；“AI 味”诊断是编辑信号，不是作者身份判定。
