# 项目图像生成判层与治理系统

本文是璃落项目所有图像生成流程的统一治理权威源。只要任务会产出图像，无论使用内置 `Image 2`、本地 `Grok`，还是后续新增的项目内生成链路，都先遵循这里的判层协议，再进入各自的模型调用方式。

## 适用范围

- 角色身份与外观反馈
- 世界 `palette`、`materials`、`atmosphere` 等风格反馈
- 构图、镜头、裁切、光线、材质、页面节奏等视觉反馈
- 批次画像、资产类型差分与提示词装配规则
- 成图后的 QA 退回标准

## 先判层，再落规则

每条新增反馈或规范都必须先回答这四个问题：

1. 这句话纠正的是事实身份、生成强调点、批次画像，还是成图后才看得出的质量问题？
2. 它影响的是全局角色、某个世界、某类资产、某个批次，还是只影响这一张图？
3. 它是长期有效、只在当前批次成立、只对这一次成立，还是还不能稳定表述？
4. 它最应该落在权威字段、提示词组装、成图 QA，还是先停留在待确认账本里？

没有完成这四问之前，不得直接把一句用户反馈写进长期 authority 或全局 prompt。

## 规则卡字段

每条长期可复用的图像规则都要能写成一张“规则卡”，最少包含：

- `ruleKind`
  - `identity`
  - `worldStyle`
  - `composition`
  - `batchProfile`
  - `safety`
  - `qa`
  - `promptStructure`
- `scopeLevel`
  - `global-character`
  - `world`
  - `asset-type`
  - `batch`
  - `single-entry`
- `persistence`
  - `long-term`
  - `batch-term`
  - `one-off`
  - `pending`
- `enforcement`
  - `authority-only`
  - `prompt-only`
  - `qa-only`
  - `authority+prompt`
  - `prompt+qa`
  - `authority+prompt+qa`
- `negativeExamples`
  - 明确写出哪些错误放法、错例或误升级路径必须避免
- `promotionGate`
  - 说明这条反馈要满足什么条件，才允许从一次性评价升级为长期规则

## 层级落点规则

### 1. Authority 层

只放“不满足就会把角色、世界或长期项目形象画错”的内容。

典型内容：

- 璃落的年龄、成年边界、发色、瞳色
- 稳定身高体态与脸型锚点
- 世界长期 `palette`、`materials`、`atmosphere`
- 角色默认展示规则

### 2. Prompt 层

只放“事实本体没错，但本次生成很容易抓不到重点”的内容。

典型内容：

- 本张图的用途与页面职责
- 本批次的镜头偏好
- 本类资产的构图优先级
- 本次任务的世界切片、光线重点、材质重心

### 3. QA 层

更适合看成图后判断的内容，默认停在 QA，不强塞回全局 prompt。

典型内容：

- 画面是否真的可读
- 是否仍然有 IP 影子、文字、水印
- 是否把局部裁切做成了卖弄身体的镜头
- 是否因为模型习惯把角色拉高、拉瘦、画尖脸

## 默认收窄原则

- 能放单图就先别升成批次规则。
- 能放批次规则就先别升成全局规则。
- 能做 QA 的问题先别污染所有提示词。
- 还不能写成绝对描述的反馈，只能停留在待确认账本。

## 反馈账本与回写

所有新反馈先进入 `visualFeedbackLedger`，保留原始语境，再拆成：

- `appliesTo`
- `abstractedTraits`
- `promptEffects`
- `writebackTargets`
- 上述规则卡字段

归档时必须把“更弱气”“更浅一些”“少一点”这类相对说法改写成绝对、可复用、可执行的目标描述。没有基线对象的比较句，不得直接沉淀到长期 authority。

## 提示词装配顺序

无论模型是谁，默认都按这个顺序组织：

1. 任务层：这张图要解决什么页面、功能或资产任务
2. 主体层：主体是谁、在做什么、哪些身份锚点不能丢
3. 世界层：空间、材质、生活痕迹和世界气质
4. 构图层：景别、机位、留白、裁切与重心
5. 光线材质层：显著影响结果的光线、色温、反射、表面
6. 安全边界层：公开安全、非幼态、不冒充实机、不写死额外 canon
7. 复核层：保留给成图后检查的问题

单次任务只装配命中的层级，不把全部长期规则全文展开进一次 prompt。没有命中的长期规则继续留在 authority 或反馈账本里，不因为“怕漏”就整批塞入当前生成。

## 低 token 与低绕圈执行顺序

图像生成任务默认不是“把所有规则都读一遍，再把所有规则都写进 prompt”。固定顺序如下：

1. 先从 authority 与反馈账本中抽本次命中的规则卡。
2. 只把命中的 `prompt` 层规则装配进单次提示词；更适合成图后判断的问题留在 `QA`。
3. 如需文档写回，先改 authority，再补直接消费者。
4. 审计、manifest、批量摘要等生成型写回放到任务末尾，只执行一次。
5. 已知会稳定写报告且触发 `EPERM` 的命令，首轮直接走正确权限路线，不先制造一次失败。

默认仍然遵守低输出阅读策略：先看统计、字段和 1–3 条样本，再打开定向原文；不直接打印整批 prompt、整份账本或整套长期规范。

## 正式收录收尾收缩

正式展示图的“归档”默认拆成两层，不再把所有动作都当成一次重流程：

1. 机器步骤只做一次：候选图升正式展示位、`sha256` 校验、`art-manifest.json` 回写、批次记录补一条正式收录说明。
2. 叙述步骤只保留必要摘要：同主题微调继续留在批次记录与 `visualFeedbackLedger`，基础总账只在“正式收录”或“新增长期可复用规则”时补一条。

执行约束：

- 同一批次、同一资产的 `v2 / v3 / v8` 这类连续微调，不因为每次换图就重复新开基础总账；仍在同一主题时优先合并。
- 只有真正影响后续路由、治理、长期 prompt 装配或公开站点正式展示位时，才升级为单独可复盘的基础记录。
- 正式展示位替换默认优先使用 `npm run site:asset:promote -- ...`，把拷贝、哈希校验和 manifest 回写收口成一条命令，减少手工串联。
- 任何“官网正式展示图”的归档，完成条件都同时包含“资产升正式位”和“直接消费者同步接线”两部分；如果站点数据、页面展示位或资源白名单还没更新到能在网站中看见，这次归档不算完成。

## 不同生成链路的执行方式

### Image 2 批次 / 站点资产

- 站点批次属于高一致性、可回归的生产链路。
- 涉及璃落身份基线、角色批次或 `Batch 00` 时，prompt 预检应以严格模式执行。
- 缺少核心身份锚点或长期构图约束时，直接阻断进入批量生成。
- 涉及站点审计或批量文档写回时，先完成 authority / 直接消费者更新，再在末尾统一运行生成器。

### Grok dry-run

- 允许先用轻量提示词探索方向。
- 仍然运行同一套 preflight，但默认以“提醒 / 待补齐”为主，而不是立刻阻断。
- dry-run 阶段的提醒必须在进入 live 前被重新审视。
- dry-run 不因为“先探索”就展开全部长期规范；仍然只装配这次命中的层级。

### Grok live

- live 属于有成本的正式草稿生成。
- 如果 prompt 明确在画璃落，却缺少核心身份锚点，preflight 直接阻断。
- 体态、脸型等扩展锚点可先给 warning，但不能长期忽略。
- live 前如需同步规则或技能说明，仍先完成 source / consumer 编辑，再决定是否运行额外生成型写回。

## 璃落的项目级身份锚点

只要 prompt 明确在生成璃落，至少要在合适层级覆盖这些核心锚点：

- `18` 岁刚成年的成年女性
- 浅红棕 / 偏绯红的红棕发
- 红色瞳孔
- 明确非幼态边界

扩展锚点在角色生产、身份基线、官网角色图等链路里应继续覆盖：

- 约 `150cm` 的娇小体型
- 自然曲线与轻微丰润感
- 柔和鹅蛋脸，不画成尖下巴或瓜子脸
