# random-story-outline-interview

## 用途与触发条件

`random-story-outline-interview` 用于从一个或多个世界中随机选择存在已确认缺口的故事大纲条目，以最小必要上下文向用户提出具体、能激发灵感的元数据问题。普通随机请求走轻量路径；只有明确要求检索、排序或比较时才扩展上下文或委派智能体。

以下请求应触发该 Skill：

- 随机选一个故事条目问我问题。
- 从都市、古代、末日、幻想、科幻、慕妮卡或全部世界里随机抽取缺项条目。
- 先给出某个不完整条目的上下文，再根据缺失内容访谈用户。
- 重复进行故事大纲灵感访谈。

## 输入与输出

### 输入

- 可选的世界限定；未指定时使用全部世界。
- 可选的条目类型、问题数量、本轮主题、随机种子和最近已提问节点排除表。
- 项目中已有的 JSON、Markdown、父子节点、玩法引用和 `missingItems`。

### 输出

- 固定结构：抽中节点、已确认上下文、当前成熟度、关键缺口、4—7 个问题、预计回写文件。
- 包含世界、风格、成熟度、父子关系、现有概念和已确认规则的上下文。
- 默认 4–7 个指向具体条目、角色、区域或状态的元数据问题。
- 每个问题都包含需要决定的事项、其设计影响和尽量丰富且有实质差异的灵感方向；选项默认可多选、组合、修改、否定或替换。

## 执行流程

1. 确定用户指定的世界范围；未指定时汇总全部世界。
2. 从含有非空 `missingItems` 的普通故事节点中随机抽取一项。
3. 用户说“随机”“随便”“问一个”或未指定筛选条件时，使用本地随机数直接抽取，不调用子智能体；只读取抽中节点的来源 JSON 和对应 Markdown。
4. 轻量路径不默认读取父节点、子节点、同级节点、世界选项、玩法目录或情节目录；仅在避免重复提问确有必要时补读直接引用。
5. 只有用户明确要求“找最完整的”“找最接近某条件的”“比较后选择”“检索匹配项”等结果时，才扩展跨节点证据，并可按需委派只读上下文智能体。
6. 只用已确认资料汇总上下文，不将候选灵感写成既定设定。
7. 区分完全没有内容的节点与已有内容但缺少制作信息的节点，再将缺口分为可文字回答的元数据和后期制作项。
8. 优先询问故事关系、进入状态、角色动机、玩家目标、核心循环、完成失败、分支结局和长期扩展规则。
9. 默认跳过地图制作、音频、像素动画、精灵表和工程制作规格。
10. 每个问题尽量提供丰富、彼此有实质差异且符合上下文的灵感选项。选项不默认互斥，用户可以多选、组合、改写、全部否定或自行指定；只有用户明确采用的内容才能确认。多个选择彼此冲突或与累计上下文冲突时，必须明确指出冲突并让用户裁决，不得自动融合。
11. 用户每次回答后，先调用 `liluo-story-outline-authoring` 把本轮全部已确认答案写入来源 JSON 与 Markdown，并把未决事项保留为具体 `missingItems`；再从更新后的来源文件、之前各轮答案和本轮答案重建累计上下文。仍有关键决定时继续聚焦提问，但不得因此暂缓写入，避免上下文压缩后丢失已确认内容。
12. 每轮写回只同步已确认答案；回答中出现的下一层未决事项要改写成新的具体缺口，不得因为阶段性写回而清空 `missingItems`。
13. 直接撰写、扩写或重构指定节点时转交 `liluo-story-outline-authoring` 并执行内容验证。

## 限制与维护要点

- 不得为方便而总是选择熟悉条目，必须从实际候选池随机抽取。
- 不得询问可从项目中直接查明的内容。
- 不得只说“请补充地图”“请补充玩法”或类似空泛问句。
- 地图、场景图或 CG 仅在叙事内容会改变剧情时询问，不询问分辨率、文件格式或制作工时。
- 对可无限扩展的区域，只询问稳定规则和进出方式，不强迫用户一次穷举全部内容。
- 写回大纲时必须重新判断成熟度，只移除已解决的缺口；旧问题全部回答不代表条目已经完整，必须完成二次缺口审计后才能清空 `missingItems`。
- 二次审计只保留当前成熟度下可执行、可回答的缺口，不把地图、音频等后期制作事项机械补入列表。
- 不伪造稳定 ID、路径或实现进度。
- Skill 的触发条件、执行流程、资源引用、输入输出或限制发生实质变化时，必须同步更新本文档。

## 情节条目联动

轻量随机访谈不默认读取 `src/game/data/plot_outline/catalog.json`。只有用户要求匹配灵感、比较适配度、寻找最佳候选，或抽中节点直接引用了必须理解的情节条目时，才检索未使用条目及部分使用条目中的待定部分。确有可能合适的真实条目时，在相关问题中写明条目名称和适配理由，作为可选方案一起询问；没有匹配项时正常提问，不为凑选项展示无关情节。候选只作为灵感，不是已确认上下文。用户明确采用后才追加真实故事节点 key，并按剩余缺口设为部分使用或已使用。具有明确前因与回收关系的内容保存在同一条目中，不按章节拆分。

登记新灵感前先比较已有小情节。若它延续同一核心冲突、因果链、前因回收，或属于既定小情节要持续收纳的段落，就扩写原条目并保留稳定 ID、使用位置与状态；相同世界、标签、人物或宽泛主题本身不足以合并。拆分与合并难以判断或存在矛盾时先询问用户，只有真正独立的内容才分配新 ID。

情节标题统一写成“主要人物-短情节名”：默认主角璃落不列入人物，其他主要人物最多列三名，超过时追加“等”，情节名保持简短。`usedBy` 保存稳定 key，`usedByLabels` 按“世界名-主线名-节点名”保存对应中文层级供界面展示。

`characters` 单独登记所有实际出现人物，包括璃落。普通 `tags` 可按情节新增；`bondageTags` 只能从已有标签中选择，且必须描述情节本身，不能因为应用节点存在某标签就自动继承。
