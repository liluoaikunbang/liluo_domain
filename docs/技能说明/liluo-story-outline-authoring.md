# liluo-story-outline-authoring

## 故事缺口候选接入

可接收 `liluo-story-gap-discovery` 中状态为 `accepted`、`accepted-with-changes` 或 `expanded` 的候选。写入前核验候选、目标节点与原始资料，不重复整套缺口分析；正式写入后记录真实 story key，并更新索引和相关验证。

## 项目索引协作

复杂定位先查询 current 的 story/graph 索引，正式撰写前核验来源 JSON 与 Markdown；修改后运行领域级增量更新和索引验证。

## 用途与边界

撰写、扩写或按模板重构指定故事节点，同步来源 JSON 与 Markdown。用户要求随机访谈、纯图结构移动、只读连续性审查或地图代码接入时不触发。

## 局部设定快速路径

仅补充已确认的世界观关系、摘要、标签、伏笔或少量既有节点正文，且不改变成熟度、主线方向、玩家流程、地图、事件、玩法、资源或进入完成条件时，按局部设定补丁处理。只读取目标 JSON/Markdown 与验证关系所需的直接关联节点；新增或移动 `side` 时额外核对直属父子树。该路径仍同步 JSON 与 Markdown、遵守来源门槛，并在结构化修改后进行一次直接校验与一次索引刷新；不读取完整模板、世界选项、成熟度参考、主线备忘、情节目录或全世界资料，除非发现冲突或需求已升级为设计决策。

## 路径与资源

- Skill：`.agents/skills/liluo-project/liluo-story-outline-authoring/`
- references：`maturity-decision.md`、`authoring-checklist.md`、`mainline-reference.md`
- 输入：完整撰写时为用户说明、条目模板、世界选项、来源节点、正文及必要父子/引用资料；局部设定补丁只需目标来源与最小关联上下文
- 输出：与真实成熟度相符的 JSON/Markdown、具体 `missingItems` 和验证结果

## 流程、限制与验证

先检查来源节点的 `status`。普通节点重建上下文，判断最高可诚实支持的成熟度，仅写已确认内容，同步两层来源并检查 key、标题、目录和 parentKey。默认在最贴近的既有节点或主线备忘中扩充；只有用户明确要求，或内容确实需要独立可玩范围、进入完成条件和制作生命周期时才新增子节点，并先记录拆分理由。不得仅因新地点、人物、单次委托或灵感拆分，且同一已确认方向不能同时留在备忘和子节点。确认目标容器后，除非来源变化、范围不清或拟修改图结构，不重复读取父子关系。`status: 主线任务` 的节点只使用“主线备忘”结构保存总体方向，供以后拆写普通剧情节点参考；不进入三档成熟度，不使用 `isTemplated`、`missingItems`、模块类型、玩法流程、状态字段、制作引用或验收内容。撰写主线下的普通节点时，必须沿 `parentKey` 读取最近的相关主线备忘及仍有效的上层备忘。事件写入 `plotRefs`，可复用知识写入 `ragRefs`，玩家可执行规则写入 `gameplayRefs`；无法可靠归类时先登记具体缺口并给用户备选，不恢复旧 Tag 字段。

## 维护要点

模板、成熟度规则、字段或验证命令变化时同步更新 Skill、references 与本文。

大型跨节点任务可委派 `liluo_context_explorer` 重建只读上下文；涉及人物、时间线或跨世界规则时可委派 `liluo_continuity_reviewer`。子智能体不修改故事，JSON 与 Markdown 由主智能体统一写入。

## 情节条目联动

撰写或完善大纲时读取 `src/game/data/plot_outline/catalog.json`，参考未使用条目及部分使用条目中的待定部分。在提出可能导致大纲回写的问题前，或执行仍需故事决策的用户授权大纲改动前，按已确认的世界、人物、地点、冲突和玩家流程检索匹配项；确有可能合适的真实条目时，在同一个问题中把条目名称和适配理由作为可选方案一起询问。没有匹配项时正常提问，不为凑选项塞入无关情节。候选不得自动并入正文；用户明确采用后才追加真实节点 key，并按剩余缺口设为部分使用或已使用。具有明确前因与回收关系的内容保存在同一条目中，不按章节拆分。

登记新灵感前先比较已有小情节。若它延续同一核心冲突、因果链、前因回收，或属于既定小情节要持续收纳的段落，就扩写原条目并保留稳定 ID、使用位置与状态；相同世界、标签、人物或宽泛主题本身不足以合并。拆分与合并难以判断或存在矛盾时先询问用户，只有真正独立的内容才分配新 ID。

情节标题统一写成“主要人物-短情节名”：默认主角璃落不列入人物，其他主要人物最多列三名，超过时追加“等”，情节名保持简短。`usedBy` 保存稳定 key，`usedByLabels` 按“世界名-主线名-节点名”保存对应中文层级供界面展示。

`characters` 单独登记所有实际出现人物，包括璃落。`storyTags` 只表示世界内故事风格；情节、知识和玩法分别通过 `plotRefs`、`ragRefs`、`gameplayRefs` 关联，不得恢复退役的 Tag 字段。
