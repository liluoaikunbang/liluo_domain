# GameView拆分整理

## 本次实现思路

这次调整的目标不是改玩法，也不是重写 Phaser 侧逻辑，而是先把 `GameView.vue` 中最安全、最外层的 UI 结构拆出来。

原来的 `GameView.vue` 同时承担了：

- 入口页展示；
- 左侧立绘展示；
- 右侧地图信息与按钮展示；
- Phaser 挂载、菜单开关、对话状态同步等逻辑。

这样写在功能还少的时候问题不大，但随着后面继续拆菜单、对话桥接、地图 HUD 等部分，单文件会越来越长，也更难判断哪些改动只是样式层、哪些改动会碰到真实玩法逻辑。

所以这次先按“最小风险”的方式推进：

- 只拆模板、样式和资源引用；
- 保持 Phaser 创建、地图同步、交互事件、对话流程都继续留在父层；
- 子组件先只接最直接的 props / emits，不引入额外状态系统或抽象层。

本轮完成后，`GameView.vue` 主要保留“游戏视图总装配”和“Phaser / 对话 / 菜单控制”职责，后续继续拆时边界会更清晰。

---

## 相关代码路径

- `src/game/views/GameView.vue`
  - 保留游戏视图总入口。
  - 继续管理：
    - `hasEnteredGame`
    - `startNewJourney()`
    - Phaser 实例挂载与销毁
    - 地图名 / 交互状态同步
    - 菜单开关与对话联动
  - 模板改为组合子组件，而不是内联全部 UI 结构。

- `src/game/views/GameEntryScreen.vue`
  - 新增入口页组件。
  - 承接原来 `entry-shell` 整块模板。
  - 承接原来 `entry-*`、`illustration-*` 相关样式。
  - 通过 `illustration` prop 接收入口图，通过 `start` 事件通知父层进入游戏。

- `src/game/views/GamePortraitPanel.vue`
  - 新增左侧立绘面板组件。
  - 承接原来左侧角色立绘与状态标签模板。
  - 承接原来 `portrait-*` 相关样式，以及该面板自身需要的 frame / tag 样式。
  - 当前仍只做纯展示，状态文案继续由父层直接传入 `状态：自由`。

- `src/game/views/GameInfoPanel.vue`
  - 新增右侧信息面板组件。
  - 承接原来地图名称、地图说明、主交互按钮、菜单按钮模板。
  - 承接原来 `info-*`、`action-*`、`menu-entry-button` 等样式。
  - 通过 `trigger-primary-action`、`open-menu` 两个事件把操作继续交回父层。

## 具体实现说明

### 1. 先把入口页从 `GameView.vue` 中独立出去

第一步先拆了最独立的入口页。

这部分的特点是：

- 不依赖 Phaser 实例；
- 不依赖地图状态；
- 不依赖对话系统；
- 只在 `!hasEnteredGame` 时显示。

因此把它抽成 `GameEntryScreen.vue` 后，父层只需要保留：

- `hasEnteredGame`
- `startNewJourney()`
- `entryIllustration`

子组件内部只负责把入口画面原样渲染出来，并在点击“新的旅程”时抛出 `start` 事件。

这样处理后，入口页视觉保持不变，但 `GameView.vue` 的 template 先减少了一整段最外层 UI 壳。

---

### 2. 再拆左侧立绘面板，保持它继续做纯展示

第二步拆的是左侧立绘区域。

这一块当前职责非常单纯：

- 显示角色立绘；
- 显示顶部状态标签；
- 不参与任何业务交互。

因此这里没有顺手引入“角色状态系统”，也没有额外做 store 或 computed 抽象，而是保持最小改动：

- `portraitSrc`：父层传入立绘图资源；
- `statusText`：父层继续直接传固定文案 `状态：自由`。

这样拆的好处是：

- 左侧面板可以先从 `GameView.vue` 中剥离；
- 但不会为了“以后可能会有状态系统”而提前增加复杂度；
- 后续如果真的要做角色状态、心情、时间段标签，也可以直接在这个组件的 props 层扩展。

---

### 3. 最后拆右侧信息面板，但事件仍交由父层处理

右侧面板虽然 UI 上也是展示壳，但它和真实交互的连接比左侧更近一些，因为它要展示：

- 当前地图名称；
- 当前地图说明；
- 当前可触发的主交互按钮；
- 菜单按钮与禁用状态。

这里本次的拆法不是把业务逻辑一起下沉，而是只做“显示 + 往外派发事件”：

- `currentMapName`
- `currentMapDescription`
- `primaryAction`
- `menuDisabled`

以及两个 emits：

- `trigger-primary-action`
- `open-menu`

因此，真正触发当前互动事件、判断菜单是否能开、同步 Phaser overlay 状态的逻辑仍然都留在 `GameView.vue`。

这样可以保证这一轮仍然只是“纯拆组件”，没有把逻辑边界一次性改得过大。

---

### 4. `GameView.vue` 收口为“组合层 + 控制层”

经过这轮拆分后，`GameView.vue` 的职责更集中在两部分：

1. **组合层**：
   - 组织入口页、左侧立绘、地图区域、右侧信息区、菜单覆盖层、对话框；

2. **控制层**：
   - 创建 / 销毁 Phaser；
   - 同步当前地图与当前交互；
   - 处理菜单快捷键；
   - 处理对话推进和分支选择；
   - 控制进入游戏流程。

这意味着后面如果还要继续拆：

- 菜单入口控制；
- 地图 HUD；
- 对话桥接；
- 通知条；

就可以围绕这个组合层继续往外拆，而不需要再从一个超长模板里硬拆。

## 开发过程中遇到的问题

### 问题 1：原样式里有一部分是被左右面板共用的，直接硬搬容易互相残留

原来的 `GameView.vue` 样式里，左右两栏并不是完全分离的。

例如：

- 面板 frame 背景风格相近；
- 顶部 tag 样式结构相近；
- 一部分 class 名写在父层，但实际只服务某一个面板。

如果直接一次性大搬运，很容易出现：

- 子组件已经接管模板，但父层还残留样式；
- 或者子组件缺了样式，导致视觉变化。

### 解决方法

这次按顺序拆：

1. 先拆入口页；
2. 再拆左侧立绘；
3. 最后拆右侧信息区；

并且每拆一个面板，就把它专属样式一起迁过去，让样式归属跟模板归属同步移动，避免父子组件之间留下太多交叉依赖。

---

### 问题 2：需要控制“只拆 UI，不顺手改业务逻辑”

右侧面板看起来很适合顺手继续往下抽，比如：

- 把 `primaryPanelAction` 再包装成专门 view model；
- 把菜单开关逻辑也一起移进去；
- 把地图信息改成独立 store。

但这些都会让这轮改动超出“Phase 1 纯拆 UI 外壳”的范围。

### 解决方法

本次明确保持：

- 子组件只接 props；
- 需要动作时只 emit；
- 业务判断仍由 `GameView.vue` 负责。

这样既达到了模板缩短、结构清晰的目的，也避免把低风险拆分变成高风险重构。

本次完成后，已确认：

- 初始打开页面时，入口页视觉保持不变；

- 左侧立绘区域视觉保持一致；
- 右侧地图名称、地图说明、主交互按钮、菜单按钮显示逻辑保持不变；
- 没有引入新的玩法逻辑或状态系统；
- `npm run build:web` 已通过；
- 用户已实际验证“没问题了”。
