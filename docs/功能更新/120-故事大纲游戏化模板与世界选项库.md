本次把故事大纲条目模板从偏小说式的内容记录升级为面向 2D 像素冒险 RPG 制作的分阶段设计模板，并按六个世界建立 `storyTags` 候选库。创建条目时可以参考世界风格、地图、玩法、状态和演出备选项，但最终一个来源 JSON 节点仍只对应一个 Markdown 大纲文件。

## 实现思路

1. 保留一个统一的故事大纲主模板，不按世界或玩法拆出多套最终模板。
2. 将条目成熟度分为“灵感”“游戏大纲”“制作设计”，不同阶段只填写当前真正需要的信息，避免一开始就被完整版字段阻塞。
3. 在主模板中增加创建整合顺序和 `moduleType` 条件检查表，按探索、调查、解谜、潜行、战斗、生存、经营等实际玩法选择相关设计项。
4. 为六个世界分别建立选项文件，在世界内部用 `storyTags` 区分具体风格。
5. 世界标签由用户定稿或按项目既有规则维护；其中魔幻、古风和末日采用固定词表，不再根据节点自动推导或扩充近义标签。
6. 候选库提供地图结构、玩家操作、事件、状态、CG、像素演出和防换皮检查方向，但正式条目只保留实际采用的内容。
7. 将 `status: 主线任务` 的节点视为主线组织容器；整理“第一个文档”时先核对来源 JSON 并跳过容器，只对第一个普通剧情节点使用条目模板。
8. 将关键缺口询问设为模板的固定步骤；项目内可确认的信息自行检索，只把会改变玩家流程、状态、分支和制作资源的问题交给用户。
9. 讨论后仍确认缺失的内容按类型、所属模块和具体缺口登记；补齐后同步清除，避免界面继续显示过期待办。
10. 为主线任务容器建立独立“主线备忘”结构，只保存总体方向、阶段参考与前后衔接，具体地图、玩法、状态和制作字段留给后续普通剧情节点。
11. 普通剧情节点撰写前沿 `parentKey` 回读相关主线备忘，区分确认约束、推荐素材与待定问题，避免子节点脱离主线方向或把备忘全文机械复制。

## 开发过程中遇到的问题

### 1. 完整模板信息全面，但日常新增条目填写压力过大

问题：地图、事件、玩法、CG、像素演出、资源和验收项全部集中后，模板能够直接服务制作，但灵感阶段也照单全填会产生大量空项或虚构占位。

解决：引入三档成熟度。灵感阶段只记录核心想法；游戏大纲阶段补齐玩家流程、地图、事件和玩法；真正进入实现时再升级到制作设计并完成资源与验收信息。

### 2. 每个世界与玩法都建立模板会导致文件数量失控

问题：同一世界可能存在多个风格，一个条目也可能组合多种玩法。如果为世界、标签和玩法分别建立最终模板，创建一个大纲块会涉及多个文件，后续同步 JSON、标题和正文也容易分叉。

解决：只保留一个主模板。世界文件作为候选库，玩法类型使用主模板内的条件表，创建时选取所需内容并整合到一个正式 Markdown 文件。

### 3. 建议选项容易被误认为当前已经存在的数据

问题：部分世界已有大量稳定的 `storyTags`，另一些世界只有一个或没有标签。若把推导出的分类和现有标签混写，后续 AI 可能误判项目现状，甚至把整份候选清单复制进 YAML。

解决：世界文件明确区分标签词表与填写候选。魔幻、古风和末日改用用户定稿的封闭词表，不再生成建议标签；候选场景、状态和引用仍不得作为占位内容批量复制。

### 4. 多个 storyTags 的组合边界不清晰

问题：同一条目可能横跨多个风格，但无限叠加标签会把数个独立玩法流程塞进一个节点，使地图、主循环和结局难以维护。

解决：约定 `storyTags` 第一项为主要风格，后续仅作为辅助。如果两个标签分别需要独立地图流程、核心矛盾和结局，应拆成两个来源 JSON 节点和两个 Markdown 文件。

### 5. 主线任务容器容易被误当成普通剧情节点

问题：主线任务节点也拥有标题和 Markdown 文件，若只按文件名或层级编号查找“第一个文档”，会把用于组织、折叠和续接主线的容器误判为可游玩条目，并错误补写地图、玩法和完成条件。

解决：创建或重构前先检查来源 JSON 的 `status`。遇到 `status: 主线任务` 时跳过该节点，从其后代中选择第一个普通剧情节点；只有用户明确要求主线总览时才维护容器内容，并使用独立的总览结构。

### 7. 主线总览即使内容很多，也容易被误套模块模板

问题：主线总览会保存多个阶段、人物成长和长期方向，看起来比普通模块更长；若据此套用“游戏大纲”，就会把尚未拆分的地图、玩法、状态和验收内容误写成已经确定的制作方案。

解决：新增独立的“主线备忘”格式。主线节点只保存已确认方向、推荐阶段、成长参考、前后衔接和以后需要确认的问题；来源 JSON 保持容器字段，正文使用 `detailLabel: 主线备忘`，不使用普通模板字段或 `missingItems`。具体章节在以后拆成普通剧情节点后再判断成熟度。

### 6. 素材不足时容易用假设填满模板

问题：当原文只有小说式情节或零散概念时，直接套用游戏大纲或制作设计会迫使撰写者编造地图、玩家操作、状态、分支和资源引用；如果每次都依赖用户主动发现缺项，又容易在后续条目中重复发生。

解决：模板固定要求先汇总真实资料。资料不足时主动询问会改变玩家目标、地图流程、控制状态、玩法、分支、结局和资源的关键问题；用户未补充的部分不编造，并按现有内容降低成熟度。

## 后续撰写规范补充

1. 撰写或完善条目前，先汇总用户说明、已有 JSON 节点、对应 Markdown、所属世界选项和可复用的真实项目资料。
2. 根据真实素材判断条目属于“灵感”“游戏大纲”还是“制作设计”，选择当前信息能够诚实支撑的最高层级，不因“写完整”而擅自拔高。
3. 素材充足时直接按模板完成，不重复询问项目内已有答案；素材不足时，只询问会影响世界、主要 storyTag、玩家目标、地图流程、核心玩法、状态、结局或资源的关键问题。
4. 用户暂时不能补充时，降到能够完成的成熟度并标明关键缺口，不使用假设、套话或整份候选清单填满模板。
5. 用户明确指定较高成熟度但素材不足时，应先说明缺少的关键材料并请求补充。
6. 主线任务节点不参与成熟度判断；即使已有详细阶段构想，也只作为主线备忘保存，待对应普通剧情节点建立后再转化为游戏大纲。用户提供的情节一旦足以形成独立冲突、玩家体验、状态衔接或持续玩法，应优先提议普通节点并请求确认，不再默认继续堆入主线备忘。
