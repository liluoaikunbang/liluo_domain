# 床事件拘束睡袋分支接入全局行走图切换

## 本次实现思路

这次需要确认并沉淀的，不是单独把 `liluo_room_bed_event` 的某个选项写死成一张新行走图，而是保证：

**当 `liluo_room` 床事件里选择 `sleep_in_tie_bag` 后，主角的全局人物行走图会切到拘束状态，并且这条链路继续复用统一的外观注册机制。**

这条能力的核心目标有两点：

1. 对话数据层只声明“切换到哪个外观 id”；
2. 真正的贴图文件、纹理 key、动画 key、场内精灵刷新，都走统一外观注册链路处理。

这样后续如果还要继续扩展：

- 受伤状态
- 换装状态
- 特殊剧情状态
- 其它地图事件触发的主角外观变化

就不需要在某个事件里重新硬写图片路径，也不需要在场景层继续加新的特判分支，只要继续复用：

- `appearanceId`
- 外观注册表
- 角色定义生成
- 运行时 `setPlayerAppearance`

这比把 `src/assets/game/sprite/liluo_walk_bondage.png` 直接塞进床事件数据里更适合项目后续继续扩地图、扩剧情、扩角色状态。

## 相关代码路径

- `src/game/data/liluo_room/dialogues.json`
  - `liluo_room_bed_dialogue` 的 `sleep_in_tie_bag` 选项声明了：
    - `playerAppearanceChange.appearanceId = "bondage"`
  - 这一层只声明外观 id，不直接写死 sprite 文件路径。

- `src/game/data/playerAppearanceRegistry.ts`
  - 统一维护主角外观注册表；
  - 这次实际使用到的注册项为：
    - `bondage`
    - `textureKey: "liluo_walk_bondage"`
    - `spriteSheetFileName: "liluo_walk_bondage.png"`
  - 同时通过 `resolvePlayerCharacterSpriteSheetUrl()` 统一把文件名解析成资源地址。

- `src/game/data/playerCharacter.ts`
  - 基于 `playerAppearanceRegistry` 批量生成主角外观定义；
  - 自动派生：
    - `spriteSheet`
    - `animationBundle`
    - `textureKey`
    - `getAnimationKey()`
  - 避免某个外观单独手写资源路径和动画 key。

- `src/game/views/composables/useGameDialogueBridge.ts`
  - 对话选项被点击后，会把 `playerAppearanceChange` 通过 `setPlayerAppearance` 往下执行。

- `src/game/views/composables/usePhaserGameBridge.ts`
  - 把 Vue 侧的 `setPlayerAppearance(appearanceId)` 继续透传给 Phaser 中的 `WorldScene`。

- `src/game/scenes/WorldScene.ts`
  - 暴露 `setPlayerAppearance()` 给桥接层调用；
  - 再把外观切换请求交给运行时地图逻辑处理。

- `src/game/systems/map/worldSceneRuntime.ts`
  - 真正负责场内主角精灵刷新；
  - 外观切换时会：
    1. 根据 `appearanceId` 找到下一个主角定义；
    2. 调用 `player.setTexture(nextCharacterDefinition.textureKey)` 更新贴图；
    3. 调用 `playerController.refreshAnimation(false)` 刷新当前朝向的待机/行动画。

- `scripts/tests/event-runner.test.mjs`
  - 已包含与本能力相关的回归测试；
  - 覆盖：
    - 床事件选项会把主角外观切到 `bondage`
    - `bondage` 外观来自复用注册，而不是事件里硬编码路径

## 开发过程中遇到的问题

### 问题 1：这次表面上像是“床事件换图”，但真正要确认的是全局外观链路有没有断

如果只看床事件文案，很容易误以为这是一个局部需求：给 `sleep_in_tie_bag` 选项加一张行走图就结束了。

但这个项目里主角行走图实际涉及：

- 数据声明
- 外观注册
- 角色定义生成
- 资源加载
- Phaser 场内角色贴图刷新
- 动画 key 刷新

只要其中一层还是旧的固定写法，就会变成“看起来能切，实际上以后扩不了”。

### 解决方法

这次重点不是另起一套新逻辑，而是逐层核对现有链路是否已经打通：

1. 床事件选项只声明 `appearanceId`
2. 外观注册表维护 `textureKey + spriteSheetFileName`
3. `playerCharacter.ts` 统一生成角色外观定义
4. 对话桥与 Phaser 桥继续透传 `setPlayerAppearance`
5. `worldSceneRuntime.ts` 在场内直接刷新玩家精灵 texture 与动画

最终确认这条链路已经成立，因此不需要为了这次需求再额外写一段硬编码路径逻辑。

---

### 问题 2：需要确认“外观状态更新”和“场内精灵真的刷新”不是两回事

仅仅把 `currentPlayerCharacterAppearanceId` 改掉，并不一定代表当前地图里的主角精灵已经变了。

如果运行时没有同步调用：

- `setTexture(...)`
- 动画刷新

那就会出现“全局状态变了，但眼前人物没变”的假切换。

### 解决方法

专门核对 `src/game/systems/map/worldSceneRuntime.ts` 中的运行时切换逻辑，确认当前实现已经在 `setPlayerAppearance()` 里完成：

1. 更新当前主角外观定义
2. `player.setTexture(nextCharacterDefinition.textureKey)`
3. `playerController.refreshAnimation(false)`

这样床事件选项切换的不只是内存状态，也会立即更新场内主角的行走图表现。

---

### 问题 3：这次实际要补的是文档沉淀，而不是继续改一遍已经存在的代码

在核对过程中，发现当前仓库里相关实现已经存在，并且测试与构建也能通过。

如果这时候不区分“新实现”和“现有能力确认”，很容易把文档写成错误的“本次新增了某某代码”，造成后续回看时混淆真实改动来源。

### 解决方法

文档里明确记录：

- 本次工作的重点是**确认并沉淀** `sleep_in_tie_bag -> bondage 外观 -> 场内行走图刷新` 这条链路；
- 当前实现依赖的核心文件路径；
- 为什么它已经满足“可复用流程，不写死固定路径”的要求；
- 本次验证所使用的测试与构建结果。

这样后续回查时，就能区分：

- 哪些是之前已经落地的实现
- 哪些是这次补充确认并登记到文档体系中的能力

1. `src/game/data/liluo_room/dialogues.json` 中，`sleep_in_tie_bag` 选项已经通过 `playerAppearanceChange.appearanceId = "bondage"` 声明主角外观切换；

5. 因此选择 `sleep_in_tie_bag` 后，主角全局行走图会切换到 `src/assets/game/sprite/liluo_walk_bondage.png` 对应的拘束状态贴图；
6. 这条链路当前已经符合“把可重复流程打通，不要僵硬写入固定路径”的要求。
