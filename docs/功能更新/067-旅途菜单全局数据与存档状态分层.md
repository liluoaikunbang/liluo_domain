# 067-旅途菜单全局数据与存档状态分层

## 实现思路

本次围绕旅途菜单的数据来源做了一次分层整理：菜单里用于展示的物品、装备、技能、任务等静态定义，不再继续放在 `views` 组件目录下，而是迁入 `src/game/data/global/`。这样这些内容会更接近“世界数据”，后续可以和地图、事件、对话一样作为 RPG 内容长期沉淀。

同时明确了存档边界：存档只保存当前档位真正变化过的运行状态，例如玩家背包里有哪些物品 id、每个物品数量是多少、某个装备槽位装备了哪个 itemId。物品名称、描述、分类、占位详情等静态定义不复制进存档，读档后由菜单 resolver 再从 `data/global` 里查定义并组合成可展示数据。

这次没有引入完整物品系统或装备操作系统，只先把现有菜单数据、运行态和存档的边界打通：

1. 静态菜单定义迁入 `src/game/data/global/gameMenuData.js`。
2. 新增 `src/game/core/gameMenuDataResolver.ts`，把 `playerRuntime.inventory/equipment` 与静态定义合并。
3. `GameMenuOverlay.vue` 从 `data/global` 读取静态定义，从 `playerRuntime` 读取当前档位状态。
4. 存档测试补充“save 只保存 id/数量/槽位，菜单 resolver 再拼显示数据”的约束。

这样后续真正加入物品、装备、任务进度时，可以继续沿用“data 负责世界定义，save 负责档位变化”的结构。

## 相关代码路径

- `src/game/data/global/gameMenuData.js`
  - 原 `src/game/views/components/base/gameMenuData.js` 的内容迁移到这里。

  - 新增 `resolveInventoryMenuCategories()`。
  - 新增 `resolveEquipmentMenuCategories()`。

  - 根据 `playerRuntime.equipment` 把已装备条目标记为 `已装备`。
  - 对存档里存在、但 `data/global` 还没有静态定义的物品或装备，归入“未归档”分类，避免数据被静默丢弃。

- `src/game/views/components/base/GameMenuOverlay.vue`
  - 静态菜单数据改为从 `../../../data/global/gameMenuData` 引入。

- `src/game/core/playerRuntime.ts`
  - 本次未大改结构，但现有 `PlayerRuntimeState.inventory`、`PlayerRuntimeState.equipment` 已作为菜单动态状态来源。

  - 新增测试：`save data stores dynamic menu state as ids while menu resolver reads static definitions`。

## 开发过程中遇到的问题

### 1. 菜单数据原本放在 views 目录，职责偏 UI

`gameMenuData.js` 原本在 `src/game/views/components/base/` 下。短期看便于组件使用，但从长期 RPG 内容扩展角度看，物品、装备、技能、任务这些定义更像世界数据，不应该绑定在某个 Vue 组件目录里。

解决方法：

- 将 `gameMenuData.js` 迁入 `src/game/data/global/`。
- 保持原有导出结构不变，让这次改动尽量只改变归属位置，不大幅重写菜单内容。
- `GameMenuOverlay.vue` 改为从 data 层导入静态定义。

### 2. 存档和静态定义需要有清晰边界

现有存档中已经有 `global.gold`、`global.desireCrystals`、`player.status`、`player.restraints`、`player.inventory`、`player.equipment`、`mapSession.flags` 等动态信息。其中 `inventory` 和 `equipment` 已经是 id/数量/槽位形式，不需要把物品名称、描述复制进 save。

解决方法：

- 保持 `saveData.ts` 的存档结构，不把静态详情写进 `GameSaveData`。
- 新增 resolver 层，专门负责把 save/runtime 状态和静态定义组合成菜单展示模型。
- 用测试明确约束：`saveData.player.inventory.old_key.name` 不存在，名称来自 resolver 使用的静态定义。

### 3. 存档里可能先出现尚未定义的物品或装备

长期开发中，事件、调试或旧档可能会让 save 里出现某个 itemId，但 `data/global` 里暂时还没有完整定义。如果菜单只显示已定义数据，玩家实际持有的信息会被隐藏。

解决方法：

- `resolveInventoryMenuCategories()` 会把未知物品放进 `runtime-unfiled-inventory`。
- `resolveEquipmentMenuCategories()` 会把未知装备放进 `runtime-unfiled-equipment`。
- 未归档条目显示原始 id，提醒后续补齐静态定义，而不是掩盖问题。

### 4. 当前还不是完整物品/装备系统

这次只是整理数据边界，不把“穿戴装备”“使用物品”“任务进度系统”等一次性做完。否则会把菜单重构扩大成新系统开发，风险太高。

解决方法：

- 只做菜单展示数据源和存档边界重构。
- 保留原有面板结构、键盘导航和占位数据。
- 后续可以在这个基础上继续扩展正式物品表、装备槽位规则、任务状态表等。

## 后续维护建议

1. 后续新增物品、装备、技能、任务等静态定义，优先放在 `src/game/data/global/` 或其进一步拆分出的子文件中。
2. 存档继续只保存变化状态，例如 `itemId -> count`、`slotId -> itemId`、任务阶段 id、剧情 flag，不要复制名称、描述、图标路径。
3. 当 `gameMenuData.js` 继续变大时，可以再拆成 `items.js`、`skills.js`、`equipment.js`、`quests.js`、`menuTabs.js`，但保持统一从 `data/global` 汇出。
4. 后续事件系统发放物品时，应只写入 `playerRuntime.inventory`，菜单显示由 resolver 自动派生。
5. 如果出现“未归档”分类，优先补齐对应静态定义，不要在 UI 里临时硬编码名称。
