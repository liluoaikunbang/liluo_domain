# 人物缩放与下半身碰撞优化

## 本次实现思路

这次调整的目标，不是去重做整套物理系统，而是在当前 `WorldScene` 的手写碰撞判定基础上，做一轮更贴近俯视角 RPG 观感的优化：

1. 保持人物当前的缩放显示比例，继续使用较小的人物尺寸，避免角色立绘在庄园地图里显得过大。
2. 把人物碰撞从“接近角色中心的小方盒”改成“只有下半身参与碰撞”的矩形碰撞盒。

这样做的好处是：

- 角色脚部仍然会被墙体、围栏、阻挡物正确挡住。
- 角色头部和上半身可以轻微压进前景边缘，视觉上会更接近传统俯视 RPG 的立体感。
- 改动范围只集中在 `WorldScene` 的碰撞判断函数，不会额外破坏现有地图读法、自动寻路和事件系统。

---

## 相关代码路径

- `src/game/scenes/WorldScene.ts`
  - 人物显示缩放仍通过 `playerScale = 0.8` 控制。
  - 新增 `playerCollisionBox` 配置，专门描述下半身碰撞盒的宽、高和纵向偏移。
  - 新增 `getPlayerCollisionBounds()`，统一生成玩家碰撞矩形。
  - 调整 `checkCollision()`，改为使用“下半身碰撞盒”去判断地图碰撞层和 blocking object。

- `package.json`
  - 本次验证时确认项目构建命令应使用 `build:web`，而不是不存在的 `build`。

---

## 具体实现说明

### 1. 保持人物当前缩放比例

场景里的主角精灵仍然使用：

- `playerScale = 0.8`

也就是继续把 32×32 的角色帧按 0.8 倍显示。

这样做的原因是当前庄园地图里的门、围栏、房屋前景和通路尺度，已经是围绕这个显示比例逐步调过的。如果把人物重新放大，角色会更容易显得“顶住门框”或者和场景比例失衡。

这次没有再额外改动人物显示比例，而是把“视觉尺寸”和“碰撞尺寸”拆开处理：

- 显示上，人物继续保持偏小、比较灵活的尺寸。
- 碰撞上，不再简单拿人物中心附近一整块区域算碰撞。

---

### 2. 把人物碰撞改成下半身矩形

之前 `checkCollision()` 里给玩家使用的是一个以角色中心为基准的小方形碰撞区域，大致相当于：

- 宽 16
- 高 16

这个方案虽然简单，但它会让角色上半身也一起参与碰撞，因此在靠近墙边、屋前、围栏、门口时，比较容易出现“头还没碰到视觉边缘就先被挡住”的感觉。

这次改成了独立的下半身碰撞配置：

- `width: 14`
- `height: 10`
- `offsetY: 6`

含义是：

- 碰撞盒比原来更矮
- 碰撞盒整体向下偏移
- 角色真正参与碰撞的区域更接近脚部和腿部

随后在 `checkCollision()` 中：

1. 先通过 `getPlayerCollisionBounds(x, y)` 生成下半身矩形。
2. 再使用该矩形四个角去检查 `collisionMap`。
3. 同时继续用这个矩形与 `blockingRects` 做矩形相交判断。

这样地图阻挡规则本身没有变，变化的是“玩家拿哪一块身体去和它碰撞”。

---

### 3. 自动寻路与事件判定保持兼容

这次没有单独去重写寻路逻辑。

当前自动寻路的可行走判断 `isTileWalkable()` 本身就是调用 `checkCollision()`，所以当人物碰撞盒改成下半身之后：

- 自动寻路会自然继承新的碰撞逻辑
- 鼠标点击移动不会和手动移动出现两套不同的阻挡标准

事件交互部分仍然通过 `getPlayerTilePosition()` 读取角色当前所在 tile，因此：

- 事件判定方式没有改变
- 不会因为碰撞盒缩到下半身，就把事件触发位置也一起改乱

## 开发过程中遇到的问题

### 问题 1：人物“视觉大小”和“碰撞大小”以前耦合得太紧

**现象：**

- 角色虽然已经缩放到较合适的显示尺寸，但碰撞判断仍然是按角色中心附近的一整块区域来算。
- 结果就是人物看起来还有空隙，实际移动时却已经撞上去了。

**解决方法：**

- 保留当前 `playerScale = 0.8` 的显示方案。
- 单独增加 `playerCollisionBox` 配置，把碰撞盒从显示尺寸里剥离出来。
- 以后如果还要继续微调手感，只需要改碰撞盒参数，不必同时改人物美术显示比例。

---

### 问题 2：要增强立体感，但不能破坏现有地图阻挡和寻路

**现象：**

- 如果直接大改碰撞系统，风险会比较高，容易把现有可走区域、自动寻路和阻挡物对象判断一起弄坏。

**解决方法：**

- 不改地图碰撞层数据结构。
- 不改 blocking object 的生成方式。
- 只改玩家碰撞盒的形状和位置，让所有已有逻辑继续复用 `checkCollision()`。

这样属于一次最小闭环改动：观感变好了，但底层规则没有被拆散。

---

### 问题 3：项目校验命令名和常规默认值不一致

**现象：**

- 初次尝试验证时使用了常见的 `npm run build`，但项目里并没有这个脚本。

**解决方法：**

- 回查 `package.json` 后，改用项目真实存在的 `npm run build:web`。
- 最终确认生产构建可以正常通过。

---

## 最终验证结果

本次已完成并确认：

- 人物当前显示缩放仍保持为 `0.8`，没有破坏现有地图比例观感。
- 人物碰撞已经改为仅下半身参与碰撞。
- 自动寻路、地图阻挡和 blocking object 碰撞仍然正常复用同一套判定。
- 用户已实际试玩确认：**当前效果没问题**。
- 使用 `npm run build:web` 已成功通过构建验证。

---

## 后续可继续扩展的方向

如果后面还想继续往“像素风冒险 RPG 的立体感”方向打磨，可以继续分阶段做：

1. 为不同角色单独配置碰撞盒参数，而不是所有角色都默认同一套手感。
2. 对房屋前景、树冠、门檐这类对象补“上层遮挡”或前景层，让人物走到下面时不仅碰撞合理，遮挡关系也更自然。
3. 如果后面接入 NPC 移动，再把 NPC 的碰撞区域也统一成脚部碰撞，而不是直接按整张图估算。

这样后续地图探索、穿行、贴边站位的体验会更稳定，也更接近一个长期可扩展的俯视冒险 RPG。
