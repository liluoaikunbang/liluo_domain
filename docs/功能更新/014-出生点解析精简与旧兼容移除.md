# 出生点解析精简与旧兼容移除

## 本次实现思路

这次调整不是继续扩功能，而是把前面为“多出生点兼容”和“旧地图兜底”临时加上的代码再收回到当前项目真正需要的范围内。

用户已经确认：

1. 当前项目里已经没有旧地图需要兼容。
2. 当前地图出生点直接走对象名方案即可，不需要再额外保留 `spawns` 配置式兼容。
3. 临时最小验证脚本后续不再长期保留。

所以这次改动的核心目标是：

- 保留 `spawnId` 透传能力；
- 但把出生点解析收敛回 `WorldScene` 直接按对象名读取；
- 删除为兼容旧结构而额外引入的抽象和临时脚本；
- 在不改变当前可玩结果的前提下，让代码更短、更直接、更符合现状。

---

## 相关代码路径

- `src/game/scenes/WorldScene.ts`
  - 现在直接使用 `worldSceneInitData.spawnId` 作为地图对象名读取出生点。
  - 删除了对 `mapData.spawns` 的额外偏移处理。
  - 删除了“旧地图仍兼容 `player_spawn`”那套兜底说明与调用。

- `src/game/systems/map/MapLoader.ts`
  - 继续保留 `spawnId` 的初始化透传。
  - 当前场景仍然可以安全接收不同地图入口传来的出生点 ID。

- `src/game/systems/map/spawnPoint.ts`
  - 本次已删除。
  - 原因是当前项目不再需要额外的出生点解析抽象层。

- `scripts/tests/resolve-spawn-point.mjs`
  - 本次已删除。
  - 原因是它只是为前一轮改造服务的临时最小验证脚本，当前不再保留。

## 具体实现说明

### 1. 出生点解析收回到场景内直接处理

之前为了兼容不同地图结构，额外拆出了 `resolveSpawnPoint(mapData, spawnId)`，会依次尝试：

- `mapData.spawns`
- 地图对象同名匹配
- `player_spawn` 兼容兜底

现在确认旧结构已经不再需要后，`WorldScene` 改回更直接的方案：

- 如果传入了 `spawnId`，就直接用它去找同名地图对象；
- 如果没找到，就退回当前地图可见内容区域中心；
- 不再额外保留旧地图兼容分支。

这样做的好处是：

- 逻辑路径更短；
- 少一个系统文件；
- 减少“当前根本用不到，但未来也未必会继续维护”的分叉逻辑。

---

### 2. 删除 `spawns` 偏移处理

前一版为了兼容配置式出生点，在 `trimRuntimeMapData` 里加入了 `mapData.spawns` 的坐标偏移修正。

由于当前项目已经明确不再使用这套结构，所以这段偏移逻辑也一起移除，避免让运行时裁切逻辑继续承担一块无实际用途的兼容代码。

现在地图运行时裁切只处理当前真正在用的数据：

- tile layer
- objects

这样更贴合当前项目数据结构，也更容易维护。

---

### 3. 删除临时验证脚本

`scripts/tests/resolve-spawn-point.mjs` 之前用于快速验证出生点解析函数的行为。

因为解析函数本身已经不再保留，这个脚本继续留下来只会形成无效维护负担，所以本次一并删除。

---

## 开发过程中遇到的问题

### 问题 1：要不要继续保留“也许以后会用到”的兼容层

**现象：**

- 前一版已经做成了更泛化的出生点解析。
- 但当前项目实际上只有对象名出生点这一种真实用法。
- 如果继续保留兼容层，会让代码看起来“更通用”，但实际增加理解成本。

**解决方法：**

- 按当前项目真实状态收缩实现。
- 不为已经不存在的旧地图继续保留分支。
- 保留必要的 `spawnId` 透传能力，但把解析回收到最直接的对象读取方式。

---

### 问题 2：验证通过后再次构建时出现 `ENOTEMPTY`

**现象：**

- 本次精简后，已先完成一次 `npm run build:web` 并通过。
- 后续在再次触发构建时，Vite 清理 `dist/assets` 目录时出现 `ENOTEMPTY`。

**解决方法：**

- 这不是本次出生点逻辑本身的编译错误，而是输出目录清理阶段的文件占用/目录状态问题。
- 同时用户已实际运行确认当前功能无报错，因此本次文档按“功能验证通过”登记。
- 后续如果再次遇到同类情况，优先检查是否有进程占用 `dist` 目录，再重新构建。

## 最终验证结果

本次已完成并确认：

- `WorldScene` 已精简为直接按 `spawnId` 读取地图对象出生点。
- 旧地图兼容逻辑已移除，不再保留 `spawnPoint.ts`。
- 临时最小验证脚本已删除。
- 用户已实际确认：当前功能没问题。
- 本地在精简完成后执行过一次 `npm run build:web`，构建通过。

## 后续可继续扩展的方向

如果后面真的出现“同一张地图多个明确出生点”的稳定需求，可以继续沿用现在这条简单路线：

- 直接在地图对象中约定多个出生点对象名；
- 由传送或场景入口传入对应 `spawnId`；
- `WorldScene` 继续按对象名读取。

这样仍然能支持 RPG 地图入口扩展，同时避免过早把系统做得过重。
