# 对话事件驱动的主角行走图切换方案评估与沉淀

## 本次实现思路

这次文档补充的重点，不是再新增一套“换行走图功能”，而是把当前项目里已经落地的这条链路正式沉淀下来：

**在地图对话 / 事件数据中，只声明主角要切换到哪个外观状态；真正的行走图资源、动画、场内精灵刷新和运行时状态更新，统一交给主角外观注册链路处理。**

当前这条链路的目标是：

1. 让 `dialogues.json` / `events.json` 只表达剧情含义，而不是直接硬写图片路径；
2. 让主角外观切换继续服务“冒险 RPG 的事件推进与状态变化”，而不是演变成临时拼贴的特殊兼容；
3. 让后续新剧情、新地图、新外观状态可以继续复用同一条入口。

以 `src/game/data/liluo_room/dialogues.json` 为例：

- `sleep_on_bed` 选项声明 `playerAppearanceChange.appearanceId = "default"`
- `sleep_in_tie_bag` 选项声明 `playerAppearanceChange.appearanceId = "bondage"`

这里没有直接写：

- `liluo_walk_source.png`
- `liluo_walk_bondage.png`
- `textureKey`
- 动画帧索引

这意味着剧情数据只负责表达“璃落现在进入了哪种外观状态”，而不直接碰底层资源细节。

这种分层对当前项目是合适的，因为主角行走图变化本质上属于：

- 剧情分支结果
- 事件状态变化
- 世界中的主角表现更新

它本来就应该沿着“对话 / 事件 → 运行时状态 → 场内角色表现”这条 RPG 链路走，而不是散落在某个组件里临时硬改。

## 相关代码路径

- `src/game/data/liluo_room/dialogues.json`
  - `liluo_room_bed_dialogue` 中的选项声明 `playerAppearanceChange`；
  - 这里只写 `appearanceId`，不直接写贴图文件路径。

- `src/game/core/dialogueExecution.ts`
  - 对话选项执行时识别 `playerAppearanceChange`；
  - 如果存在 `setPlayerAppearance` 执行上下文，就把 `appearanceId` 往下透传。

- `src/game/core/eventExecution.ts`
  - 事件执行链路同样支持 `playerAppearanceChange`；
  - 说明这套机制不只可用于对话选项，也能复用于地图事件动作。

- `src/game/views/composables/useGameDialogueBridge.ts`
  - 把对话选择中的 `playerAppearanceChange` 桥接到 `setPlayerAppearance`；
  - Vue 侧不直接处理贴图，只负责把“切换外观”的意图交给运行时。

- `src/game/views/composables/usePhaserGameBridge.ts`
  - 把 Vue 侧的外观切换请求继续透传给 Phaser 世界场景。

- `src/game/scenes/WorldScene.ts`
  - 对外暴露 `setPlayerAppearance()`，作为 UI / 对话桥接层进入 Phaser 场内逻辑的入口。

- `src/game/systems/map/worldSceneRuntime.ts`
  - 真正负责场内玩家精灵的更新；
  - `setPlayerAppearance()` 中会：
    1. 通过 `appearanceId` 找到下一个主角定义；
    2. 校验对应纹理是否已经加载；
    3. 更新 `activeCharacterDefinition`；
    4. 调用 `setCurrentPlayerAppearance()` 同步全局当前外观；
    5. 调用 `player.setTexture(...)` 切换场内玩家贴图；
    6. 调用 `playerController.refreshAnimation(false)` 刷新当前朝向动画。

- `src/game/data/playerCharacter.ts`
  - 统一维护主角外观注册表 `playerAppearanceSpriteSheets`；
  - 当前默认包含：
    - `default -> liluo_walk_source.png`
    - `bondage -> liluo_walk_bondage.png`
  - 同时负责：
    - 解析 spritesheet URL
    - 生成 `GameCharacterDefinition`
    - 生成主角资源 bundle
    - 管理当前全局外观 id

- `scripts/tests/event-runner.test.mjs`
  - 覆盖对话选项驱动的外观切换；
  - 已验证：
    - `sleep_in_tie_bag` 会把主角外观切到 `bondage`
    - 默认外观来自 `liluo_walk_source.png`
    - 拘束外观来自 `liluo_walk_bondage.png`

- `scripts/tests/player-spritesheet-normalization.test.mjs`
  - 验证主角 spritesheet 已不再依赖早先为两套不同行走图加入的 normalization 兼容元数据。

## 开发过程中遇到的问题

### 问题 1：看起来像“某个床事件切图”，实际要确认的是整条外观链路是否合理

表面上，这次需求像是在 `liluo_room` 的床事件里给某个选项换一张行走图。

但如果只把某张图片路径塞进某个对话选项里，后面会很快出现问题：

- 其它地图事件没法复用
- 外观资源路径会散落在剧情 JSON 中
- 后续改贴图文件名时要全局回找剧情数据
- 场内动画 key 和运行时刷新逻辑也容易脱节

### 解决方法

这次确认并沉淀的，是“外观切换链路”而不是“单个事件特判”：

1. 数据层只声明 `appearanceId`
2. 执行层只识别 `playerAppearanceChange`
3. 运行时统一从 `playerCharacter.ts` 取外观定义
4. 场内精灵刷新由 `worldSceneRuntime.ts` 统一处理

这样以后继续增加主角新状态时，不需要在对话数据里重新硬写路径。

---

### 问题 2：只改全局状态不等于当前地图里的主角真的换图了

如果只是把“当前外观 id”改了，但场景里的 player sprite 没同步更新，那么玩家看到的会是：

- 状态逻辑上已经切换
- 画面上角色却还是旧外观

这种情况最容易让后续排查变得混乱。

### 解决方法

本次专门确认 `src/game/systems/map/worldSceneRuntime.ts` 中的 `setPlayerAppearance()` 已经在同一个入口里完成：

1. 外观定义切换
2. 全局外观状态切换
3. `player.setTexture(...)`
4. `playerController.refreshAnimation(false)`

也就是说，这套方案切换的不只是内存里的状态，而是会立即反映到地图中的主角行走图与当前动画表现上。

---

### 问题 3：当前方案是否安全、是否适合继续复用

这里真正需要评估的是三件事：

1. 对话 / 事件数据里写 `appearanceId` 会不会太脆弱；
2. 这条链路是不是过度设计；
3. 以后其它剧情还能不能继续用。

### 解决方法

核对现有实现后，当前判断是：

- **安全**：运行时会校验 `appearanceId` 是否存在、纹理是否已加载，失败会明确报错而不是静默吞掉；
- **合适**：它正好服务“剧情驱动的主角外观变化”，符合项目当前的冒险 RPG 方向；
- **可复用**：可继续复用于主角在其它地图、其它剧情、其它事件中的外观状态切换。

但同时也明确它的复用边界：

- 适合主角外观切换；
- 不应直接被当成“所有 NPC 通用换装系统”去无限外推。

也就是说，它是当前阶段很合适的主角外观方案，但暂时不需要为了未来可能的复杂角色系统而提前做过度抽象。

---

### 问题 4：之前为了两套不同行走图差异加入过 normalization / 校准兼容，评估方案时要把这段历史影响纳入考虑

项目里之前为两张尺寸不一致的主角行走图加过 spritesheet 归一化 / 校准处理。

如果外观切换方案仍依赖那一层兼容，就意味着：

- 当前外观机制并不干净
- 资源切换还夹着特殊补丁
- 后续新增外观时风险仍然较高

### 解决方法

这次评估时同步确认：

- 归一化兼容逻辑已从主角资源链路中移除；
- `playerCharacter.ts` 当前直接声明每个外观自己的 spritesheet 配置；
- 默认外观已经切回 `liluo_walk_source.png`；
- 拘束外观继续保持 `liluo_walk_bondage.png`。

因此，当前“对话 / 事件驱动的主角行走图切换”方案，已经建立在更干净的资源定义基础上，而不是继续依赖旧兼容层。

---

## 最终验证结果

本次沉淀后的结论如下：

1. `src/game/data/liluo_room/dialogues.json` 中已经可以通过 `playerAppearanceChange.appearanceId` 声明主角行走图切换；
2. `dialogueExecution.ts`、`useGameDialogueBridge.ts`、`WorldScene`、`worldSceneRuntime.ts` 已经形成完整执行链路；
3. `playerCharacter.ts` 统一维护外观 id 与 spritesheet 资源映射，剧情数据不直接耦合图片路径；
4. 当前方案对主角剧情外观切换来说是安全的、合适的，并且具备可复用性；
5. 其复用边界应明确限定在“主角外观状态切换”，而不是提前扩成全角色通用换装框架；
6. 在移除旧的 spritesheet normalization 兼容后，这条链路现在更加直接、可维护。

本次确认过程中涉及并已通过的相关测试：

```bash
node --test scripts/tests/event-runner.test.mjs scripts/tests/player-spritesheet-normalization.test.mjs
```

验证结果：

- 共 17 项测试全部通过；
- 已覆盖默认 / 拘束外观资源指向；
- 已覆盖 `liluo_room` 床事件对话切换外观；
- 已覆盖主角 spritesheet 不再声明 normalization 兼容元数据。

补充说明：

- 本次是对现有实现逻辑的评估与沉淀，不是额外新增另一条外观切换路线；
- 本次没有新增 `src/assets/game` 下的新素材文件，因此无需更新 `docs/游戏素材图片清单.md`。
