# 地图资源索引与按地图动态加载

## 本次实现思路

这次调整的目标，是把原先集中写在 `BootScene` 里的地图图片注册拆开，改成更适合长期扩地图的结构：

1. `BootScene` 只加载游戏启动一定会用到的全局资源。
2. 每张地图自己维护一份资源索引。
3. 地图切换统一经过 `MapLoadingScene`，由它按 `mapId` 动态补齐当前地图所需资源。
4. 资源索引仍然通过 `data/registry.ts` 统一接入，避免出现多套入口。

这样做之后，地图越多时不会继续把所有图片都堆进 `BootScene`，同时也保留了当前项目已经在用的 `registry -> MapLoadingScene -> WorldScene` 主流程。

---

## 当前推荐目录结构

这次落地后的资源组织结构如下：

```text
src/game/
├─ core/
├─ scenes/
│  ├─ BootScene.ts
│  ├─ MapLoadingScene.ts
│  └─ WorldScene.ts
├─ systems/
│  └─ map/
├─ data/
│  ├─ assets.ts                # 通用资源清单类型、排队加载与 prepare 工具
│  ├─ globalAssets.ts          # 全局共享资源（BootScene 加载）
│  ├─ registry.ts              # 地图注册表单一入口
│  └─ liluo_estate/
│     ├─ map.json
│     ├─ events.json
│     ├─ dialogues.json
│     ├─ meta.ts
│     └─ assets.ts             # 当前地图自己的资源清单
└─ views/
```

如果后面继续新增地图，推荐按同样结构扩展：

```text
src/game/data/<mapId>/
├─ map.json
├─ events.json
├─ dialogues.json
├─ meta.ts
└─ assets.ts
```

其中职责划分建议保持为：

- `assets.ts`：定义 `manifest` 和可选 `prepare()`。
- `registry.ts`：把地图数据、默认出生点、资源 bundle 一起注册出去。
- `BootScene`：只管全局共享资源。
- `MapLoadingScene`：只管当前地图进入前的资源动态加载。

## 相关代码路径

- `src/game/data/assets.ts`
  - 新增资源声明类型：`image`、`spritesheet`
  - 新增 `queueAssetBundle()`，统一把未加载资源加入 Phaser Loader
  - 新增 `prepareAssetBundle()`，统一执行资源加载后的补充准备逻辑

- `src/game/data/globalAssets.ts`
  - 提取当前全局共享资源
  - 现阶段先放主角行走图 `liluo_walk`

- `src/game/data/liluo_estate/assets.ts`
  - 为 `liluo_estate` 单独维护地图资源清单
  - 把地形、老 tileset、围栏、传送门等资源从 `BootScene` 移出
  - 把围栏 frame 切片逻辑放进 `prepareFenceTexture()`

- `src/game/data/registry.ts`
  - 地图注册项新增 `assets?: GameAssetBundle`
  - `liluo_estate` 现在通过 registry 同时注册地图数据和资源 bundle

- `src/game/scenes/BootScene.ts`
  - 只保留全局资源加载
  - 启动后直接进入 `MapLoadingScene`

- `src/game/scenes/MapLoadingScene.ts`
  - 接管地图资源动态加载
  - 进入地图前先根据 `mapId` 查 registry
  - 只加载当前还未进入 texture cache 的资源
  - 加载完成后执行 `prepareAssetBundle()`，再进入 `WorldScene`

## 具体实现说明

### 1. 把资源声明从场景硬编码改成 manifest

之前的 `BootScene` 里直接手写了多段：

- `this.load.spritesheet(...)`
- `this.load.image(...)`

这种写法在只有一张地图时还能接受，但地图一多就会出现两个问题：

1. 资源定义和地图归属关系不清楚。
2. 首次启动就把很多暂时不会进入的地图资源一并加载。

这次改成 `GameAssetBundle` 后，每张地图都可以自己描述：

- 要加载哪些资源
- 资源 key 是什么
- 属于 `image` 还是 `spritesheet`
- 加载完成后是否还要做补充 prepare

这样资源定义和地图本身就绑定起来了。

---

### 2. BootScene 只保留全局共享资源

现在 `BootScene` 不再知道庄园地图要用哪些 tileset、围栏、传送门贴图。

它只做两件事：

1. 注册启动期一定会用到的全局共享资源。
2. 进入 `MapLoadingScene`。

目前全局资源先只保留了：

- `liluo_walk`

这样后面如果有：

- 通用 UI 图
- 通用对话框装饰
- 所有地图共用的角色基础图

也可以继续放进 `globalAssets.ts`，而不是重新把地图资源塞回 `BootScene`。

---

### 3. MapLoadingScene 接管按地图动态加载

这次最关键的变化，是让 `MapLoadingScene` 从“单纯中转场景”变成“地图进入前的资源准备场景”。

现在流程是：

1. `BootScene` 传入要进入的 `mapId`
2. `MapLoadingScene` 用 `resolveWorldSceneInitData()` 得到目标地图
3. 再用 `getMapRegistryEntry(mapId)` 取出该地图的 `assets`
4. 调用 `queueAssetBundle()`，只把还没加载过的资源排进 loader
5. `create()` 阶段调用 `prepareAssetBundle()`
6. 最后再进入 `WorldScene`

这样以后地图切换时，如果目标地图的资源已经在缓存里，就不会重复加载；如果没加载过，才在切图前补齐。

---

### 4. prepare 逻辑跟资源归属一起下沉

围栏这类资源不是“加载完图片就可以直接用”，还要补 frame 切片。

之前这段逻辑写在 `BootScene.create()` 里，会导致两个问题：

1. 它其实是庄园地图相关逻辑，但位置却放在了全局启动场景。
2. 以后如果别的地图也有自己的特殊处理，`BootScene` 会继续膨胀。

这次把它放到 `liluo_estate/assets.ts` 的 `prepareFenceTexture()` 里，再通过 `prepareAssetBundle()` 调用，资源归属就更清楚了：

- 庄园地图自己的资源
- 庄园地图自己的资源后处理

都放在庄园地图目录里维护。

## 开发过程中遇到的问题

### 问题 1：资源 URL 原先散落在 BootScene，后续地图会越来越难维护

**现象：**

- 原先所有图片 URL 和 `load.xxx()` 都集中写在 `BootScene`。
- 地图一多，启动场景会越来越像一个“全项目素材堆放点”。

**解决方法：**

- 新增 `GameAssetBundle` 结构。
- 每张地图通过自己的 `assets.ts` 维护资源清单。
- `registry.ts` 继续作为统一接入口。

---

### 问题 2：地图资源不只是加载，还可能带有额外 prepare 逻辑

**现象：**

- 比如围栏图 `fence_wood` 还需要在纹理上补多个 frame。
- 如果只抽 manifest，不处理 prepare，后面地图资源的后处理逻辑还是会散回场景里。

**解决方法：**

- 在 `GameAssetBundle` 里增加可选 `prepare(scene)`。
- 由 `MapLoadingScene.create()` 在资源实际可用后统一调用。

---

### 问题 3：动态加载后要避免重复排队和重复注册

**现象：**

- 地图切换时，如果每次都无脑再次 `load.image/load.spritesheet`，会产生重复加载风险。

**解决方法：**

- 在 `queueAssetBundle()` 里先检查 `scene.textures.exists(asset.key)`。
- 已在缓存中的资源直接跳过，只补齐未加载项。

## 最终验证结果

本次已完成并确认：

- `BootScene` 已收缩为只处理全局资源加载。
- `MapLoadingScene` 已开始负责按地图动态加载资源。

## 后续可继续扩展的方向

1. 后面如果出现多张地图共用同一批素材，可以继续补一层 shared bundle，而不是每张地图都重复写一遍。
2. 如果地图切换频率变高，再考虑增加“卸载长期不用资源”的策略，但现阶段先以稳定可玩为主，不急着过度设计。
3. 后续新增地图时，优先直接按 `meta + map + events + dialogues + assets` 的完整结构落地，避免再回到集中手写加载的模式。
