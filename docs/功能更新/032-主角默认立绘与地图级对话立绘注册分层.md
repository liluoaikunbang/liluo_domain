# 主角默认立绘与地图级对话立绘注册分层

## 本次实现思路

这次调整的目标，不只是把立绘图片路径替换掉，而是顺手把“全局默认立绘”和“地图专属立绘”两种职责明确拆开。

当前项目里：

1. 主角璃落的默认立绘应该属于全局资源；
2. 璃音的对话立绘目前只在 `liluo_estate` 庄园地图使用，更适合跟随地图剧情注册；
3. 未来主角也会有一部分只在特定地图使用的立绘，因此结构上不能把“主角”简单等同于“永远全局”。

基于这个前提，这次没有继续把立绘配置直接散落在各个地图对话文件里，而是把对话立绘的定义统一收口到 `src/game/data/dialoguePortraits.ts`，再在里面明确拆成：

- `globalDialoguePortraits`：全局默认立绘；
- `mapDialoguePortraits`：地图专属立绘；
- 各自对应的 asset bundle：负责把图片真正接入加载链路。

这样后续如果要继续补：

- 主角全局默认立绘；
- 主角地图专属立绘；
- NPC 地图专属立绘；

都可以沿用同一套结构继续往下扩展，不用再返工一次分层。

## 开发过程中遇到的问题

### 问题 1：主角和 NPC 的立绘注册规则不同，但未来主角也不一定全部全局

如果这次只把“璃落放全局、璃音放地图”硬编码到两个文件里，当前能跑，但以后主角只在某张地图出现特殊立绘时，又会重新遇到“到底该放哪”的问题。

### 解决方法

这次直接在 `src/game/data/dialoguePortraits.ts` 里把结构分成两层：

- `globalDialoguePortraits`
- `mapDialoguePortraits`

这样“是否全局”由资源职责决定，而不是由“是不是主角”决定。后续主角的某些特殊立绘如果只在地图中使用，也可以自然挂到地图级配置里。

---

### 问题 2：原先地图文件里直接拼接图片 URL，不利于复用和扩展

庄园地图原本是在 `liluo_estate/dialogues.ts` 里直接声明璃音立绘 URL 和 manifest。短期可用，但同类资源一多，就容易出现：

- 路径散落；
- key 命名分散；
- 地图级和全局级资源边界越来越模糊。

### 解决方法

把立绘定义抽回 `dialoguePortraits.ts` 统一维护，再导出：

- 立绘数据对象；
- 对应 asset bundle。

地图对话文件只负责“用哪张立绘”，不再重复关心 URL 和 manifest 的拼装细节。

---

### 问题 3：一开始用错了验证脚本名

这轮调整后原本先尝试执行了：

```bash
npm run build
```

但项目实际没有 `build` 脚本，只有：

- `build:web`
- `build:offline`

### 解决方法

改用项目当前真实存在的脚本：

```bash
npm run build:web
```

并确认构建通过，且产物里可以看到新的 `LiLuo` 与 `LiYin` standee 图片已被正常打包。
