# 地图旅途菜单与ESC快捷入口

## 本次实现思路

这次功能的目标，是先把地图中的“旅途菜单”入口立起来，让当前项目更像一个真正可游玩的像素风冒险 RPG，而不是只能移动和触发对话。

这次没有直接把背包、任务、存档等完整系统一口气做完，而是先把**菜单入口、开关逻辑、禁用控制和整体视觉骨架**搭好，后续再往里面逐步填正式内容。

实现时主要分成四部分：

1. **先给地图界面补菜单入口与快捷键**
   - 在 `GameView` 右侧信息栏底部增加固定的“菜单”按钮。
   - 同时补上 `Esc` 快捷键，让玩家在地图中能更像常规 RPG 一样直接呼出菜单。
   - 两种入口共用同一套开关状态，避免逻辑分叉。

2. **把菜单做成独立覆盖层组件**
   - 新增 `GameMenuOverlay` 组件专门负责菜单层渲染。
   - 当前先放入“物品 / 技能 / 任务 / 回顾 / 存档 / 设置”等栏目占位。
   - 内容区先保持最小可用占位，后续可以继续接正式系统界面。

3. **补上“多数时候可点、少量场景不可点”的控制能力**
   - 菜单按钮默认可用，但在对话进行中或场景明确禁用时自动变为不可用。
   - Vue 侧通过 `sceneMenuAvailability` 接收 Phaser 场景同步过来的状态。
   - 这样后续如果某些演出、事件、过场、强制交互阶段不允许开菜单，就可以直接复用这套开关机制。

4. **让菜单打开时真正影响地图交互**
   - 菜单和对话框一样，会把“当前有 UI 覆盖层打开”的状态同步回 `WorldScene`。
   - 这样玩家开菜单后，不会继续误触地图互动或把场景输入逻辑搞乱。

---

## 相关代码路径

- `src/views/GameView.vue`
  - 在右侧信息栏底部增加固定“菜单”按钮。
  - 新增 `isMenuOpen`、`sceneMenuAvailability`、`isMenuButtonDisabled` 等状态。
  - 增加 `openMenu()`、`closeMenu()`、`handleMenuShortcut()` 等菜单开关逻辑。
  - 将菜单显隐状态和对话框状态统一同步给 Phaser 场景。

- `src/components/base/GameMenuOverlay.vue`
  - 新增旅途菜单覆盖层组件。
  - 负责遮罩、右上角关闭 `X`、左侧栏目列表、右侧占位内容区与整体菜单样式。
  - 当前采用同色系半透明深紫底板，保持和现有界面一致的幻想 RPG 氛围。

- `src/game/core/createPhaserGame.ts`
  - 给 `createPhaserGame()` 增加 `onMenuAvailabilityChange` 回调接线。
  - 在 Vue 与 `WorldScene` 建立菜单可用状态同步。

- `src/game/scenes/WorldScene.ts`
  - 增加菜单可用性回调、UI 覆盖层开关、菜单禁用状态与原因字段。
  - 提供 `setUiOverlayOpen()`、`setMenuAvailabilityChangeCallback()`、`setMenuDisabled()` 等方法。
  - 让 Phaser 场景可以把“当前能不能开菜单”这一层状态交给 Vue UI。

## 具体实现说明

### 1. 菜单入口放在右侧信息栏，并保留 `Esc` 快捷打开

这次菜单没有做成隐藏在某个深层页面里的网页按钮，而是直接挂在地图界面右侧信息栏底部。

这样处理有两个好处：

- 入口稳定，玩家在大部分时候都能直接找到。
- 视觉上更接近传统 RPG 的“地图内功能菜单”，而不是额外跳网页页签。

同时又补上了 `Esc` 快捷键：

- 如果当前已经在旅途中，并且菜单允许打开，按 `Esc` 可以呼出菜单。
- 如果菜单已经打开，再按一次 `Esc` 会关闭菜单。

这让操作习惯更自然，也更符合玩家对游戏菜单的直觉。

---

### 2. 菜单按钮支持禁用，并且能显示明确的禁用来源

本次不是简单做一个永远能点的按钮，而是把“是否能开菜单”当成正式状态来处理。

当前按钮会在这些情况下自动不可用：

1. 还没进入旅程时
2. 对话框进行中
3. Phaser 场景主动声明当前阶段不能打开菜单时

其中第三种情况是通过 `sceneMenuAvailability` 从 `WorldScene` 同步回来的。`WorldScene` 提供了：

- `setMenuAvailabilityChangeCallback()`
- `setMenuDisabled()`
- `emitMenuAvailability()`

这样后续如果某个地图事件、演出镜头、强制推进流程中不允许开菜单，就不需要在 Vue 页面里写死特殊判断，而是可以由场景本身直接控制。

---

### 3. 菜单覆盖层做成独立组件，先保证风格与结构成立

当前 `GameMenuOverlay` 不是完整系统界面，而是一个可继续扩展的菜单骨架。

它目前具备：

- 半透明同色系遮罩与面板
- 左侧栏目切换
- 右侧主内容区
- 右上角小型关闭 `X`
- 简单淡入淡出过渡

栏目先放了：

- 物品
- 技能
- 任务
- 回顾
- 存档
- 设置

内容区目前还是占位说明，但布局已经按后续真正接系统内容的方向搭好：左边保持较窄，把更多宽度留给右侧主体内容。

这次样式重点也不是做很花哨的弹窗，而是先保证：

- 看起来属于当前项目世界观与配色
- 不抢过地图与角色立绘主视觉
- 后续接真实内容时不用推翻重做

---

### 4. 菜单打开时，会同步通知 Phaser 当前有 UI 覆盖层

如果只是把一个 Vue 菜单盖在 Phaser 上面，但不通知场景层，容易出现两个问题：

- 玩家开着菜单时还能继续触发地图互动
- 输入状态残留，关菜单后可能出现误触

这次在 `GameView` 中通过 `watch([showDialog, isMenuOpen], ...)`，把“对话或菜单是否正在打开”统一同步给 `WorldScene`。

`WorldScene` 则通过：

- `setUiOverlayOpen()`
- `setDialogueOpen()`

来接收这一状态。

这样菜单和对话框在场景侧都被视为“当前有 UI 覆盖层打开”，输入处理会更稳定，也方便后续继续扩展别的覆盖 UI。

---

### 5. 关闭按钮与左栏宽度根据实测做了二次收口

这次菜单样式不是一次定死的，而是在用户实际查看后又继续收了一轮细节。

后续调整包括：

- 把关闭按钮改成右上角的小 `X`
- 将 `X` 顶到更靠右上的边缘，避免压住内部内容
- 缩窄左侧栏目列宽，让“物品”等栏目更贴边
- 尽量把横向空间留给右边主体内容区

这样菜单更像 RPG 中的功能面板，而不是普通网页对话框。

## 开发过程中遇到的问题

### 问题 1：菜单入口要固定可见，但又不能在所有情况下都无脑可点

**现象：**

- 如果按钮永远可点，遇到对话中、事件中、特殊演出中就容易和当前流程冲突。
- 如果把判断逻辑全写死在 Vue 页面里，后面地图事件一多会很难维护。

**解决方法：**

- 在 Vue 侧保留统一的 `isMenuButtonDisabled` 计算状态。
- 同时从 `WorldScene` 提供菜单可用性回调，把场景层的禁用意图同步回来。

这样按钮既能在大部分时候固定可用，也能保留少量场景下的正式禁用能力。

---

### 问题 2：菜单打开后不能只“视觉上盖住地图”，还要真正影响底层输入

**现象：**

- 单纯加一个前端遮罩，表面看像菜单打开了，但底层 Phaser 可能还在继续响应互动输入。

**解决方法：**

- 在 `GameView` 里把菜单和对话统一视作“UI 覆盖层”。
- 再通过 `syncOverlayStateToPhaser()` 把状态同步给 `WorldScene`。

这样地图层能明确知道当前是否应该冻结一部分输入响应。

---

### 问题 3：菜单当前只是占位，但视觉上不能太像临时开发面板

**现象：**

- 如果只是一块普通白底弹层，会和现有画面气质脱节。
- 如果一开始做得太重、太复杂，又会拖慢功能落地。

**解决方法：**

- 先做同色系半透明深紫菜单底板。
- 保持结构清楚、配色统一、层次足够，但不堆太多复杂装饰。
- 先把栏目与主体布局定下来，后续再逐栏替换成正式系统内容。

这样既保证当前“可玩、可看”，也不会阻塞后面的系统扩展。

---

### 问题 4：关闭按钮会和内容区形成视觉挤压

**现象：**

- 初版关闭按钮占了上方布局空间。
- 调整成右上角按钮后，又出现和内部排版挤在一起的感觉。

**解决方法：**

- 把关闭入口改成绝对定位的小 `X`。
- 再根据用户实测反馈，把它继续顶到右上角边缘。
- 同时缩窄左栏，把更多空间还给主体内容。

经过这一轮收口后，菜单的整体比例更自然了。

---

### 问题 5：文档必须等用户实际确认无问题后再补

**现象：**

- 按项目规则，功能不能只算“代码写完”，还必须经过用户实际测试确认。

**解决方法：**

- 先完成实现与构建检查。
- 再根据用户连续反馈，迭代调整关闭按钮和布局细节。
- 最后在用户确认“没问题了”后，再补写本份文档。
